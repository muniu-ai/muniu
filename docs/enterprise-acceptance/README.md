# 企业经营平台验收基线

E0.2 冻结两模式任务、故障规格、评估口径和旧测试覆盖关系。冻结规格不保存产品通过成绩，也不启动模型、Sales 或企业微信。后续局部工程证据单独记录，当前见[E1 证据映射](e1-evidence.md)。实现依据为[完整计划](../proposals/enterprise-operating-platform-2026-11-02.md)第 10、11 节，结构契约见 [ADR 0015](../adr/0015-enterprise-operating-platform.md)。

## 文件与执行

`baseline.json` 是可解析的验收规格，`baseline.lock.json` 固定原始文件 SHA-256 与版本。包含 30 个共享业务场景，分别形成内置和 Sales 模式的 60 项任务，以及 31 项安全恢复规格。每模式按五条流程各分四项调试、两项留出，共 20/10；每项 Agent 任务执行三轮，重复运行不增加独立样本数。

从仓库根目录执行：

```sh
npm run verify:enterprise-acceptance-spec
node --test scripts/test/enterprise-acceptance-spec.test.mjs
```

第一条检查材料结构、摘要、旧测试文件与 UI 门禁是否存在。第二条验证规格校验器能拒绝篡改、遗漏、重复与伪造结果。它们不能替代任何业务、权限或端到端门禁。

`syntheticCompany` 提供合成成员、客户、服务版本、合同、订单、项目、付款期和收款。模式分别使用独立租户，并保留第三个隔离探测租户。金额使用 CNY 整数分，业务时钟固定为北京时间对应的 `2026-11-02T01:00:00.000Z`。只使用测试 OIDC，不能将这些身份用于生产。

## 要求、故障与旧覆盖

`requirements` 将 B01—U01 的 17 项要求映射到负责工作包和必需门禁。`scenarios` 保存具体输入、预期事实和关联要求；`tasks` 引用同一场景，禁止模式私自覆盖输入或预期。涉及模式差异的预期要求两端分别完成负责系统批准，不能把本地候选显示为两端均已生效。

`safetyTasks` 固定故障注入位置及预期，覆盖异步撤权、未知效果、投影重建、联合灾备和连接器故障。其中包含外部动作成功、本地承诺、operationKey 和回执全部晚于恢复点而丢失的场景；核对完成前保持隔离。

每项安全规格也执行三轮，适用模式由其 `modes` 字段固定。业务和安全任务每轮均使用等价初始数据、权限及外部测试状态，在独立命名空间执行，不继承前轮成果、记忆或重试结果。单轮内未知动作始终使用原 operationKey，未核对前不得清理状态或开启新操作绕过核对。

`legacyCoverage` 登记十组原业务不变量及测试文件，`legacyUiGates` 登记六个旧 UI 门禁的替代目标。旧实现、旧测试与旧 UI 门禁均须在 E6.3 的替代实现及真实断言通过、证据登记完成后才能退出。E0—E6.2 不允许提前删除。

## 评分与证据

发布成绩仅使用留出集，调试集独立报告。人工基线对同一输入、权限、量表和工具独立执行一次；Agent 三轮的首次提交均计入首次验收率，失败和返工不能删除。每模式首次验收率不低于人工基线；包含准备、审核、纠错与返工的人工总时间至少下降 20%，分流程报告成绩和波动。

计时只排除没有人工活动的系统或外部等待，并保存暂停原因。先计算同一 Agent 任务三轮的人工时间平均值，再按模式汇总与对应人工基线比较。金额、权限、来源等程序检查必须全部通过；安全恢复任务全部通过，不能用平均分抵消失败。

多人同时参与时累计每个人的活动时间。共用准备和审核时间按该批次的任务数等额分摊，人工基线与 Agent 任务使用相同规则，并保存分摊原始记录。

留出集不能用于选择模型、提示、参数或工具。若根据留出结果调整配置，原发布成绩失效，必须由独立负责人准备新的未见留出集、重新冻结配置后评估。不能在同一留出集上反复调参再报告发布成绩。

复核职责在本基线固定为独立且具备相应业务资格的人员，不得复核本人制单的高影响业务事实。E7 执行前必须绑定实际复核人与人工基线操作者，固定模型版本、提示摘要、资料和权限快照、工具及价格版本。当前没有这些人员的实测数据，也没有已冻结的真实模型运行配置，因此不得开始或宣称离线质量验收通过。

结果写入单独的获准证据目录，不回填本基线的 `executionStatus`。记录两仓提交、锁文件和契约摘要、运行配置、每轮来源证据、全部模型费用、人工活动时间与失败原因。未知费用保持未知，不能记为零。仓库只保存脱敏摘要，原始资料保留在获准证据存储。

试点还需十个工作日、至少 100 个主动候选、准确率至少 90%、越权为零；样本不足继续观察。容量和联合恢复环境及阈值固定在 `capacity`，RTO 包含核对和实际业务恢复。

## CI 与后续工作包

当前 Node CI 执行规格检查，`test:boundaries` 同时运行校验器测试。`ciGroups` 记录后续分组，`gates` 记录原方案要求的 12 个新命令及负责包。这些字段保留 E0.2 冻结时的未实施状态，不回填后续结果。`verify:business-domain` 已由 E2 接入真实领域、持久权限和 HTTP 断言；当前结果见[E2.2 验收记录](../verification/enterprise-e2-2-2026-11-04.md)。`verify:enterprise-operating` 与 `verify:enterprise-operating-postgres` 由 E4.1 提供；后者包含 E3 故障断言并接入 Node CI，结果见[E4.1 验收记录](../verification/enterprise-e4-1-2026-11-04.md)。其他门禁按各负责工作包登记，没有添加空脚本或成功占位任务。

真实运行条件逐项记录在 `executionPrerequisites`。人员、模型配置及试点企业尚未绑定；测试 OIDC、Sales 部署、企业微信测试企业、容量及联合恢复环境尚未核验。每项列明受影响门禁；“尚未核验”不表示相应资源一定不存在。后续包须记录真实就绪证据，不能据现有代码推断环境已具备。

E1/E2 实现身份、权限及领域规则，E3/E4 实现执行和评估，E5 实现提供方与真实连接，E6 实现 Web，E7 执行真实依赖、质量和容量验收。每组只有具备真实断言后才能接入 CI；环境不足须记录未运行及原因。

变更基线必须显式发布新版本，保留旧版本及改变理由，通过相同校验与独立复核后更新摘要。已经开始评估的留出集、评分口径和失败结果不能为提高成绩而修改。实际复核人员、外部测试账号和模型配置是后续执行条件，不能用合成身份或模型替身代替。
