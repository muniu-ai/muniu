# 持久动作与预算预留

E3.1 增加共享预算账户和提供方动作协调器，复用现有 Kernel 事务、Job、租约、Worker 与受保护事件日志。企业身份和对象权限由[E3.2 执行准入](enterprise-execution-admission.md)装配，提供方在 E5 实现；本文记录 E3.1 原语边界。

## 一次动作的持久过程

1. `prepare` 在事务中核对当前执行主体、授权范围和期限，为稳定 `operationKey` 预留预算，保存不可变动作内容与 outbox。一个动作占用一个专用 Execution。
2. `requestApproval` 使用中央工具政策请求精确执行批准，绑定工具、版本、参数摘要、目标对象、授权版本和期限。等待人员时不创建 Job。同一操作换用新的请求键重发时，新增独立请求记录事件以保存可重建的幂等映射，原动作版本、预算和 Job 保持不变。
3. `enqueue` 重验当前权限、批准与预算账户，在同一事务中保存动作、Job、Job 投影和 outbox。
4. Worker 领取既有持久 Job。派发前验证提供方身份、版本、对象归属与动作能力，再通过 `begin` 重验当前授权、批准和租约，同时持久提交工具承诺与预算承诺。
5. 提供方返回匹配原操作、动作摘要和租户范围的确定回执后，动作、Execution、工具承诺、预算和 Job 在同一事务中结算。

当前提供方写入均要求精确人工执行批准。中央批准路径检查当前 Principal、工作区成员和批准权限，动作协调器另要求批准主体为 human；销售、财务等企业业务角色资格由 E3.2 接入，当前模块不独立授予这些资格。限定策略预授权属于 E3.2 的后续准入集成；业务批准仍是独立事实。正式报价动作必须携带业务批准引用，引用的真实性和当前资格由业务权限适配及提供方再次核验。

动作协调器要求受信 Host 注入同步 `assertCurrent` 检查。空实现只能用于聚焦测试，不能用于产品装配。回调抛错才表示拒绝；异步函数、Promise、布尔值或其他返回值均拒绝，防止把未等待的权限判断当作通过。该回调负责业务对象、字段、来源版本、当前提供方绑定及阶段所需资格。

## 未知结果与停止

工具承诺一旦提交，任何未获确定回执的中断均保留原操作与预算。Worker 重启或再次领取该 Job 时不重放提供方写入。原操作处于已提交或待核对期间，同一提供方和同一业务对象不能用新的操作标识绕过阻塞。

`markUnknown` 将动作及 Execution 标记为待核对，保留预算预留。`reconcile` 要求受信 Host 的同步政策回调验证核对主体当前权限，E3.2 负责区分获准人员与内部服务主体。通过检查后才接受已核验确定回执，核对原 `operationKey`、摘要与作用域；成功回执须引用业务事实或人员决定。重复提交相同回执与费用不重复扣费，回执或费用不一致时拒绝。

回执的来源可信性必须由 Host 提供方适配保证；结构校验不能证明任意客户端提交的 JSON 是真实回执。`usageForReceipt` 必须同步返回已核验用量，只允许受信、版本化计量器提供，不能采用模型自报费用。需要异步查询的计量结果应先由受信提供方取得，再交给同步回调；回调异常、Promise 或无效用量均不能完成结算，已承诺动作保留待核对。当前没有自动轮询回执入口；E5 提供方与后续监督流程使用 `getReceipt` 后调用核对端口。

工具承诺提交前取消会释放未使用预算、使批准失效并终结 Job。承诺提交后，即使提供方尚未被调用，只要没有确定回执，就必须保留原操作与预算并先核对，不能显示为已取消或重新发起动作。陈旧租约不能提交回执或终结 Job；核对完成时使仍在途的旧 Job 租约失效，并同步物理 Job 与投影。

Worker 准入失败发生在工具承诺之前时，可以持已验证租约登记内部失败、释放未用预算；这不授予失权主体继续读取内容或执行外部操作的权限。承诺之后的回执结算同样属于内部记账，不因负责人撤权而伪造动作未发生。

## 预算账户

预算使用整数 token、十进制整数字符串金额和明确币种。租户、工作区、Goal、节点等范围可以建立父子账户；预留与实际费用在同一事务中作用于整条父账户链。各层是同一笔费用的额度约束，不能相加为重复支出。

账户按租户、工作区和范围确定唯一标识，配置与期限固定；不能通过重建相同范围账户重置已花费用。创建、预留与承诺都检查当前成员及主体，只有预留负责人可以承诺该预留。父账户的币种、作用域和期限也限制子账户。

预留状态为 reserved、committed、unknown、settled 或 released。只有未承诺预留可以释放；已承诺或费用未知必须保留。确定计量超出预留时记录实际费用和超额，不截断事实，也不重新执行；超出账户额度后阻止新增调用。已关闭账户不能继续承诺，但允许内部完成既有结算。

低层记账函数不独立验证提供方签名或 Worker 租约，必须由动作协调器或等价受信事务调用。企业管理员的配置上限、运行槽位与模型评估预算在 E3.2/E4 接入这些账户，不能把账户原语当作完整企业额度管理。

## 验证边界

从工作树根目录执行 `npm run verify:enterprise-actions` 运行预算、动作与提供方 Worker 的聚焦检查。

聚焦测试使用真实 SQLite、加密 CAS 和既有 Worker，提供方为合成故障注入实现。场景包括等待批准不占 Job、共享父账户限额、未知费用保留、实际超额、不同批准不能串用、主体停用、队列内撤权、工具承诺先于外部调用、外部成功后响应丢失、关闭并重开数据库及重建投影后不重放、陈旧租约和核对后失效旧 Job。

`npm run verify:enterprise-actions-postgres` 使用独立 PostgreSQL、两个 Worker、回环 HTTP 合成提供方和可强制退出的子进程，验证事务派发、响应丢失、重建、陈旧租约、未知预算保留和回执去重。容器限制为 192MiB、0.5 CPU，结束后删除；仅用于合成验收。

完整企业身份装配、真实 Sales/企业微信和容量仍由 E3.2、E5/E7 验收。历史记录见[E3.1 初次验证](verification/enterprise-e3-1-2026-11-02.md)，本轮记录见[E3.1 基线复验](verification/enterprise-e3-1-review-2026-11-04.md)。
