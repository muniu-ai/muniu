# OPC 经营管理体系与木牛产品改造方案

木牛的 OPC 应服务于一人公司的持续经营：确定经营方向，理解客户，组织产品与协作资源，完成获客、成交、交付和回款，再用经营事实调整下一轮行动。机会验证是其中的探索流程，已有客户和订单可以直接进入经营流程。

日期：2026-10-09。源码基线：`af69167aa55070120c12c1b39e629ed9faf54415`。本文依据用户对产品定位的纠正设计目标体系；现状、目标能力和分期分别列明。文中拟议对象与接口不代表已经实现。

本轮实施范围为 M1，采用理由见 [ADR 0014](../adr/0014-opc-business-management.md)，当前入口见[经营使用指南](../guides/business.md)。M2–M4 及表中更细的获客、伙伴和财务专项仍是后续设计，不能视为本轮已交付能力。

采用三个产品原则：以客户价值组织业务；以可追溯事实支持判断；以周期复盘修订方向。不能从这些观点推导出“所有操作都自动化”，也不能把作者观点直接当成适用于每家公司的经营结论。

## 2. 经营主线

经营方向与资源约束 → 客户需求 → 产品与服务 → 获客与成交 → 订单履约 → 验收与资金记录 → 客户经营 → 复盘与下一周期。

市场探索和机会验证贯穿这条主线。售后反馈可能触发产品修订，交付成本可能改变报价，客户流失可能推翻客户分群假设。系统应保留这些联系，而不要求所有业务都从访谈开始。

一人公司负责人兼任多个经营角色。系统按业务责任组织工作，不要求用户虚构部门或雇员；Agent 承担有明确输入、成果和验收条件的任务，负责人保留经营决定与授权。

## 3. 完整经营体系

| 领域 | 经营者要回答的问题 | 管理对象 | 主要产出 |
| --- | --- | --- | --- |
| 经营方向与战略 | 为谁创造什么价值？本期聚焦什么、暂缓什么？ | 经营主体、商业模式、客户分群、价值主张、战略版本、周期目标、经营预算 | 本期经营计划、资源取舍、验证假设与复盘日期 |
| 客户洞察与验证 | 客户的真实问题、购买条件和替代方案是什么？ | 机会、需求、访谈、信号、实验、反证、验证决定 | 经核实的客户问题、继续或停止的依据 |
| 产品与服务 | 卖什么、交付什么、如何定价和验收？ | 产品目录、服务包、版本、定价、交付标准、成本假设 | 可销售版本与明确承诺；订单引用确定版本 |
| 品牌与获客 | 通过哪些渠道接触客户，投入是否有效？ | 渠道、内容计划、活动、线索、渠道成本、联系授权 | 可审阅内容、获客实验、来源明确的线索与转化记录 |
| 客户与销售 | 当前应跟进谁？客户是否认可条款？ | 客户、联系人、沟通、商机、报价版本、合同或确认依据、订单 | 待跟进清单、正式报价、成交或流失事实 |
| 交付与客户服务 | 能否按承诺完成？客户是否验收？ | 履约项目、里程碑、工作任务、交付版本、变更、验收、售后、续约 | 可核对交付物、客户验收记录、问题处理与复购计划 |
| 资金与经营分析 | 还应收多少？实际收支怎样？哪些业务值得继续？ | 应收、应付、分期、收款、付款、退款、费用、凭证、对账 | 分币种资金视图、逾期清单、现金预测与经营结果分析 |
| 资源与协作 | 哪些能力自己做，哪些交给 Agent 或合作伙伴？ | 人员职责、合作伙伴、服务能力、可用时间、约定、授权、任务预算 | 资源安排、履约责任与明确的协作交接 |
| 知识与经营复盘 | 哪个判断发生变化？下期具体改什么？ | 指标快照、经营决定、原因、客户反馈、失败经验、模板、复盘版本 | 周/月复盘、下一周期行动、可复用经验及其适用条件 |

机会验证通过不等于形成可持续业务。客户付款也不证明长期价值；还需观察交付成本、满意度、复购、现金占用和经营者的时间投入。

## 4. 周期机制与指标

M1 每个工作区对应一个经营主体；客户、订单、资金和指标均属于该主体，不跨工作区合并。首版支持服务和项目型业务的人民币（CNY）台账，金额按整数分保存；多币种和多主体汇总另行设计。系统同时维护业务单据的生命周期和经营周期。订单跨月未完成时继续存在，不因月度复盘而关闭。周期目标、预算和复盘必须有明确开始、截止时间和币种。

| 节奏 | 系统提供的工作视图 | 负责人留下的决定 |
| --- | --- | --- |
| 每日 | 到期跟进、交付、待验收、待收款、异常与待批准事项 | 先做什么、延期什么、需要谁补充事实 |
| 每周 | 获客与商机变化、交付风险、资金缺口、实验反馈 | 下一周行动与资源调整 |
| 每月或自定义周期 | 目标与实际、产品及客户贡献、经营成本、关键假设变化 | 下一周期战略版本、保留与停止事项 |
| 事件触发 | 大额退款、重要客户流失、范围变更、关键指标异常 | 是否改变承诺、暂停动作或提前复盘 |

指标必须展示来源、时间范围、口径和数据完整性。首版先计算可由现有业务记录可靠得到的指标，不生成没有来源的增长建议。

| 指标 | 口径要求 |
| --- | --- |
| 新增线索、成交转化 | 定义线索去重方式、统计窗口和转化分母；缺少数据时显示未建立口径 |
| 成交金额 | 客户确认的有效订单金额，按币种分组；不能用报价草稿金额替代 |
| 到期应收 | 到期付款计划减去有效分配的实收及调整，保留退款和取消影响 |
| 实收、实支、净流入 | 以资金发生时间汇总已登记且未被冲销的流水；不同币种不直接相加 |
| 毛利与获客成本 | 只有成本归集和归因规则完整时计算；否则显示已记录成本及缺口 |
| 交付及时率 | 绑定约定期限、实际交付及客户验收时间；范围变更保留原约定 |
| 复购、续约与流失 | 定义适用产品、观察期及客户身份；单次成交业务不强套订阅指标 |
| 经营者时间 | 区分销售、交付、维护和探索投入；模型费用单独列示 |

收入、利润、现金流和模型费用是不同口径。初期的人工收支记录不能宣称完成银行对账、税务处理或法定会计核算。

## 5. 业务模型与关键约束

| 对象 | 应保留的内容与关系 | 状态或版本约束 |
| --- | --- | --- |
| 经营主体与周期 | 主体、业务范围、目标客户、方向、时间边界、资源限额 | 战略修订追加版本；旧订单不随战略变化而被改写 |
| 客户与联系人 | 身份、需求、来源、联系渠道、联系授权及沟通事实 | 客户合并有审计，不把多次沟通算成多个客户 |
| 产品/服务版本 | 范围、排除项、价格、币种、交付方式、验收标准 | 已被报价和订单引用的版本不可覆盖 |
| 商机与报价 | 客户需求、产品版本、个性化范围、条款、付款计划、有效期 | 报价修订不覆盖已发版本；成交必须有人确认客户接受依据 |
| 订单与应收 | 固定条款、报价版本或已有合同快照、客户确认依据、付款安排 | 一次成交只产生一个订单；取消及金额调整保留原因和原值 |
| 履约与验收 | 里程碑、交付版本、成果引用、客户决定、返工与范围变更 | 内部接收 Agent 成果与客户验收分别记录；不能用执行成功标记客户满意 |
| 资金记录 | 收支类型、整数最小货币单位、币种、发生时间、订单分配、凭证来源与核实人 | 已确认记录不可覆盖；更正走冲销或调整；支持部分付款与退款 |
| 伙伴与任务 | 能力、责任、约定、来源对象、输入版本、预算和验收 | 业务预算与 Agent 执行预算分开；外包结果也需验收 |
| 经营复盘 | 截止时点、事实版本、指标定义、解释、反证、决定与后续行动 | 保存不可变快照；迟到流水通过新版本修订，不能暗改旧结论 |

合同到期、交付承诺、退款义务和授权期限归属于对应业务对象。负责人登记依据、期限与处理状态，经营总览展示未完成事项；专门的合规判断另行处理。

已有订单可依据原合同或客户确认快照独立建单，不要求补造报价。建单时固定登记截止日、已交付比例、期初已收款与未结金额；期初已收款只参与订单余额，不计为登记当期的现金流。截止日之后的收支分别登记，不允许同一笔历史收款同时作为期初数和新流水。

订单应收余额等于确认金额加减订单调整，减去期初已收和有效实收，再加已退金额。退款表示实际资金流出，本身不等于减免客户义务；若退款同时降低订单价款，需另有金额调整与依据。收款分配不超过应收余额；退款不超过尚未退款的有效收款，且与订单币种一致。录错收款的冲销撤销其台账影响，不表示真实退款。

例如，已有订单 1,000 元，截止日前已收 400 元，则期初应收为 600 元，本期实收为 0。后续收款 300 元，应收为 300 元；再实际退款 100 元，应收恢复为 400 元。若这次退款源于双方同意总价降为 900 元，还需登记调减 100 元，应收才回到 300 元。机会的 `evidenceLevel = paid` 只表示已确认付费证据，不能生成流水、减少应收或标记订单已收款。

人员录入、外部系统回执和模型推断需要标明来源。录入客户确认或流水凭据时，系统记录“由谁根据什么登记”，不会把人工文字变成银行核验或客户电子签名。

## 6. Agent 如何参与经营

经营负责人从业务对象发起任务，不必先配置一组虚拟部门。不同经营职责可以对应能力模板，是否交给多个 Agent 取决于任务依赖、成本与验证能力。

| 任务 | 固定输入 | 可接收成果 | 人的决定 |
| --- | --- | --- | --- |
| 经营诊断与计划 | 当前战略、周期事实、资源约束 | 问题、证据、取舍与计划候选 | 采纳方向及投入 |
| 市场和客户研究 | 客户问题、已授权资料、公开来源 | 支持与反对证据、缺口、访谈方案 | 确认假设及实验 |
| 获客与销售准备 | 产品版本、客户需求、渠道约束 | 内容草稿、跟进清单、报价候选 | 发布、联系、价格与条款 |
| 交付协作 | 固定订单、范围、资料权限、标准 | 工作计划、交付物、检查证据 | 范围变更、对外交付、客户验收登记 |
| 收支核对 | 订单、应收、已授权流水与凭证 | 匹配候选、差异和逾期清单 | 确认账务事实；资金动作另行授权 |
| 经营复盘 | 指标快照、客户反馈、原假设 | 变化解释、反证、下一轮行动候选 | 修订战略和采用经验 |

沿用 Goal、Execution、审批、预算、成果验收和未知结果核对。经营周期关联多次有界任务；一个长期运行的聊天会话不能替代经营系统。

外联、发布、签约和资金动作必须各有适配器、权限、审批、稳定操作号和可核对回执。尚未接通的动作显示为待人工处理；效果未知时进入核对，不能自动重发。首个完整经营流程可以全部基于已在线下发生的事实登记。

## 7. 产品与入门改造

产品名称使用“OPC 经营管理”。保留“机会验证”作为明确的子入口，验证 Agent 继续承担其原职责；新增 Agent 职责须有真实上下文与成果检查支持。

工作台建议以经营总览为入口，按“经营计划、客户与销售、产品与服务、获客、订单与交付、收支、协作资源、知识与复盘”组织。设置继续容纳工作区、模型、插件、成员和外部连接。专业视图展开技术信息，业务行为保持一致。

首次设置提供三条入口：

1. 探索新业务：建立经营方向，按需创建机会验证。
2. 已有客户：建立客户和需求，直接准备产品或正式报价。
3. 已有订单：根据原合同或确认快照录入条款、截止日、已交付、期初已收和未结款项，不强制补做访谈。

基础经营记录不依赖模型连接；用户可以先建台账，在首次调用 Agent 时再连接模型。首屏描述应说明经营范围，具体动作是否支持则在对应页面说明。

示例：独立设计师建立目标客户与品牌设计服务包，登记来源明确的客户，形成报价并记录客户确认，按里程碑交付，记录返工或验收，再登记预付款、尾款及外包成本。月底对照客户满意度、实际投入和资金记录，决定下一轮改进定价、渠道或服务范围。

## 9. 分期与完成标准

整个体系按以下子计划推进，首个可用版本必须能完成一笔业务，而不只展示模块入口。

| 子计划 | 可用结果 | 验收依据 |
| --- | --- | --- |
| M1 经营事实管理 | 服务和项目型业务，CNY 台账：经营计划、客户、产品版本、商机和订单、交付验收、应收及收支、周期复盘；已有业务可直接录入 | 从建客户到结单复盘的真实 API/UI/CLI 流程；金额和状态互相一致；重试不重复成交或入账 |
| M2 经营 Agent | 计划、跟进、交付风险、应收核对和复盘任务使用当前业务上下文 | 固定输入版本和授权；结果只能作为候选；修改或撤销来源后旧候选失效 |
| M3 渠道与协作网络 | 获准渠道、伙伴、外包、外部系统接入与受控执行 | 每项动作单独验证批准、回执、撤权、未知结果及恢复 |
| M4 持续经营 | 周期触发、跨任务协调、模板与经验迭代、可核对经营分析 | 无静默扩大授权；每项判断可追溯；按周期验证结果与采用决定 |

完整体系还应按实际经营形态扩展实物库存采购、订阅续费、税票和多主体核算。先冻结各专项对象、连接器和口径，再承诺对应业务能力。

M1 使用独立的工作区经营事件流，客户、产品、报价、订单和流水各有标识；同一事件流的版本冲突检查使订单调整与资金分配可以原子校验。这会使一个工作区的写入串行化，适合首版一人公司；并发规模变化时，再设计分领域事件流与跨对象事务。机会验证继续使用独立的机会事件流。

M1 至少覆盖以下反例：旧订单 1,000 元、期初已收 400 元、已交付一半，可不建报价直接录入且不污染本期现金；报价变更不能改写旧订单；部分交付与部分回款独立；退款及冲销不能重复计算；取消不能抹除已发生资金事实；跨工作区引用被拒绝；模型建议不能直接写入成交、客户验收或资金事实；删除查询投影后能从受保护事件恢复。

工程门禁遵循仓库基线，并新增完整经营流程、资金计算、权限撤销、幂等并发、重建和桌面流程回归。真实模型、渠道和银行接口需要各自的授权环境；固定响应测试和人工台账不替代这些验收。
