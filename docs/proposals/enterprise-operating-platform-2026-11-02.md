# Muniu 企业经营平台完整执行计划

状态：2026-11-02 用户已批准按本计划实施，当前执行 E0.1。本文是本轮产品重构、跨仓接入和工程验收的统一依据；实施与验收进度另行记录。

目标是建设面向服务与项目型企业的持续经营平台。系统围绕经营目标、客户、项目、交付和回款组织人员与 Agent，在明确授权内持续推进工作，以业务事实和可核对成果判断完成情况。

## 1. 审核摘要

### 1.1 已确认的产品选择

| 项目 | 本轮采用的决定 |
| --- | --- |
| 客户 | 服务与项目型企业，重点覆盖销售、项目交付和应收管理 |
| 产品模式 | 内置经营管理与外部业务系统连接，两条路径同时验收 |
| 交付方式 | 托管 SaaS、浏览器优先；Desktop 与 CLI 共用 Host 契约 |
| 办公渠道 | 企业微信，先支持内部员工明确请求、通知和工作台审批 |
| 外部业务系统 | 木牛 AI 销售作为首个真实参考连接器 |
| 自主程度 | 分级授权；允许授权范围内动态拆解、并行和重规划 |
| 研发方式 | 按完整产品研发投入组织，依赖明确后并行开展工作包 |
| 历史约束 | 尚未上线，不兼容旧 API、数据库、界面、插件协议或本地状态；不开发迁移、别名或双版本运行机制 |

### 1.2 本次需要审核的新增设计决定

1. 企业业务按独立对象建模，废止整个工作区共用一份经营聚合的设计。
2. 采用一个持久执行体系，动态计划替代固定团队限制；模板保留为经过验证的起点。
3. 企业身份、对象权限、业务审批和执行授权分别判断，所有 Agent 行为都具有可追溯的责任人。
4. 内置与外部业务使用同一对象和动作协议，每种业务事实只有一个负责系统。
5. 首期采用模块化后端、独立扩容的 Worker 与连接器执行进程，暂不引入新的工作流引擎或消息中间件。
6. 新建浏览器产品入口和共享业务界面包，重构 Host 的产品服务；不以旧目录结构决定新边界。
7. 首次启动使用新状态目录和新数据库命名空间。用户机器上的旧状态、凭据和其他工作树保持原样，不能因无需兼容而直接删除。
8. 首期采用受控企业配置和第一方流程库。客户上传代码、自动生成并运行生产代码、开放第三方插件市场不在本轮范围。

按已批准工作包及依赖实施。设计和工程验收不等于生产上线授权；生产环境、真实客户资料和外部账号须按试点清单落实。实施授权不包含生产部署、公开发布或旧状态清理。

## 2. 产品范围与完成标准

### 2.1 企业与经营范围

一个 Tenant 对应一家客户企业；一个 Workspace 对应一个经营主体的数据与业务授权边界。部门和项目是工作区内的对象，不为每个部门或项目复制一套客户台账。首期验收一个企业一个经营主体，跨主体合并另行立项。

支持人民币整数分、Asia/Shanghai 业务日期、服务目录、单次及分期合同、部分交付、部分验收、部分回款、退款和订单调整。所有业务时间同时保存发生日期和系统记录时间。外部事件另存来源时间与接收时间，迟到事件不能暗改历史复盘。

首期不提供库存制造、采购供应链、税票、银行自动对账、法定会计、多币种结算、跨法人合并、自动资金划转或法律签署。报价出包和业务收支登记属于本轮范围。

### 2.2 五套经营流程

| 流程 | 输入与自动工作 | 人员决定 | 可核对的结果 |
| --- | --- | --- | --- |
| 商机跟进 | 客户需求、阶段、跟进记录；提取缺项、准备下一步、创建获准内部待办 | 客户归属、销售承诺、对外发送 | 责任人明确的商机与跟进记录，不能用生成建议代替客户回应 |
| 方案报价 | 已确认需求、有效服务价格及条款；整理方案、计算报价候选、检查遗漏 | 正式报价、折扣、合同条款、客户接受与订单生效 | 固定报价版本、批准证据、正式文件及独立客户确认记录 |
| 项目交付 | 生效订单、范围、里程碑和资源；拆解工作、发现延期、准备成果 | 范围和费用变更、内部接收、客户验收 | 交付版本、客户验收证据及仍未完成的承诺 |
| 应收跟进 | 付款计划、有效收款和调整；识别到期、准备催收材料 | 对外催收、到账与退款登记 | 可追溯应收余额和下一步；不以发送提醒认定到账 |
| 经营复盘 | 周期目标、业务记录、成本与执行用量；解释偏差、整理证据和建议 | 下周期目标、资源与预算调整 | 固定期间、口径和来源版本的复盘，以及关联的后续工作 |

### 2.3 界面与岗位

主导航固定为经营总览、待我处理、客户与销售、项目与交付、资金与复盘、知识与成果。管理区包含组织与权限、Agent 与流程、连接与模型、用量与审计。Coding 位于专业工具区，不成为经营用户的首次使用步骤。

总览显示本期目标、实际变化、关键异常和责任人。任务区显示正在执行、排队、等待外部变化、等待人员、待核对及已完成；每个统计数字都链接到使用同一查询条件的明细。

Agent 以职责配置，不预置虚构企业组织。首期提供经营协调、销售支持、项目协调、应收分析、经营分析、成果复核六种职责定义。职责绑定能力、资料范围、默认模型和验收规则，不能自动取得同名人类岗位的权限。

通知只在需要人员行动、重要异常或成果可用时发送。一般进展保存在事项内；同一事项与状态版本的通知去重，人员可订阅每日摘要。首期审批在已登录工作台完成，企业微信消息携带不含敏感正文的入口链接。

### 2.4 首次使用

管理员创建企业、验证身份、邀请成员、选择经营模式、设置对象权限和预算，再启用流程。缺少模型时可以管理业务；缺少额度或授权时，Agent 只显示配置缺项。观察模式可以做获准且已计费的评估，但不创建主动执行任务。

## 3. 目标架构与代码边界

### 3.1 组件决定

| 组件 | 本轮职责 | 明确边界 |
| --- | --- | --- |
| Host | 唯一组合根、认证入口、业务应用服务、API 与事件订阅；按领域拆分路由和服务 | 不在单个路由文件堆叠业务逻辑；模型不直接操作数据库 |
| Kernel | 通用授权、预算预留、审批承诺、持久调度、租约、取消和恢复 | 不导入客户、报价、项目等产品类型或插件 |
| Agent Runtime | 模型会话、受保护上下文、工具调用、消息投递和结构化报告 | 不决定客户是否验收、订单是否生效或资金是否到账 |
| Task Orchestration | 计划图校验、就绪节点、重规划规则、预算分配、模板解析 | 私有模块，由 Host/Worker 调用；不另建状态引擎 |
| Enterprise Services | 成员、部门、对象授权、职责分离、租户配额 | 只由可信服务端身份创建执行主体 |
| Business 插件 | 经营对象、命令、领域事件、金额规则、指标和流程贡献 | 通过公共 contracts 与 plugin-sdk 工作，不导入 Kernel 或私有编排包 |
| Connector 执行进程 | 企业微信接入、Sales 读写、回执和来源状态 | 使用有限能力和短期凭据；不能直接写 Host 业务表 |
| Storage | PostgreSQL/SQLite、事件和受保护内容、投影、CAS、KMS、备份恢复 | 查询投影不是事实来源；不将客户正文放入明文诊断 |
| Web/共享 UI | 新建 apps/web 与 packages/product-ui；共享页面、状态订阅及生成客户端 | 不复制权限和金额规则；原生文件能力通过 Shell 端口注入 |
| Desktop/CLI | 使用同一 Host 的辅助入口 | 首期 Desktop 支持连接托管服务，CLI 保留管理、检查与自动化；不以本地隐式身份访问云端 |

新增私有企业服务包；将 plugins/opc 中适用的领域规则审查后转入新的 business 插件，旧 OPC 产品壳和旧聚合结构退出本轮目标产品。机会验证作为客户洞察流程保留。Coding 作为可选受控能力继续保留。

Host 仍统一装配运行组件；Worker 和连接器启动入口接受 Host 装配配置，不自行构建第二套业务控制面。连接器能力通过 plugin-sdk 注册，新增贡献协议覆盖来源接收、对象读取、动作准备、动作执行和回执查询。现有针对单一询价的私有业务执行服务由通用动作协调替代，行业规则归业务提供方。

### 3.2 存储与运行

企业部署以 PostgreSQL、S3 兼容对象存储和 Vault/KMS 为基线，持久 Job 和 outbox 仍由 PostgreSQL 管理。首期使用 PostgreSQL 全文检索与关系索引检索资料，不引入独立向量数据库；嵌入检索可在后续质量评测支持后增加。

控制与业务逻辑保持模块边界，初期共用物理数据库，按命名空间和仓储端口隔离；Sales 使用自己的数据库。所有可重建的产品状态来自 KernelEventV1 及受保护内容引用。新增领域事件表达实际命令结果，不把可变投影快照当作来源。

租户条件由服务端作用域注入，数据库查询同时使用租户约束与最小权限账号。后台任务和资料读取也执行同一检查。跨租户访问测试必须覆盖 API、SSE、搜索、导出、对象存储引用、Job 和连接器回执。

同进程插件仍是可信代码，只装载平台审查的固定版本。首期不开放客户自定义代码运行。Coding 工作在必需沙箱中；沙箱不可用则停用 Coding 能力，不能影响纯经营只读能力，也不能退回无隔离执行。

### 3.3 企业认证

浏览器采用标准 OIDC Authorization Code + PKCE，由服务端处理令牌并建立 HttpOnly、Secure、SameSite 会话；写请求校验 CSRF/Origin。OIDC subject 与租户成员显式绑定，不依据邮箱域名、企业微信昵称或客户端 tenantId 自行授予权限。

企业微信机器人凭据与浏览器登录凭据分开管理。管理员通过已验证的企业身份登记 corp/user 到成员的映射，成员可见范围由服务端权限控制。邀请接受、移除、禁用和账号重绑定均留下事件。权限撤销不等待模型完成当前回答才生效。

托管服务首期通过人工开通租户和配额交付，提供用量与成本报告；自助购买、计费收款和服务商市场上架不作为首轮工程出口条件。

## 4. 业务模型与双模式协议

### 4.1 核心对象

| 领域 | 对象 | 核心约束 |
| --- | --- | --- |
| 经营方向 | OperatingObjective、MetricDefinition、BusinessReview | 期间、指标定义、目标值、责任人和来源版本固定；AI 不改指标算法 |
| 客户销售 | Customer、Contact、Opportunity、ServiceVersion、QuoteVersion、Contract、Order | 客户归属明确，报价引用有效版本，客户接受与订单生效分别记录 |
| 交付 | Project、Milestone、DeliveryVersion、CustomerAcceptance、ChangeRequest | 订单与项目关联，范围变更可追溯，内部成果接收不等于客户验收 |
| 资金记录 | PaymentSchedule、Receipt、Refund、Expense、Adjustment | 人民币整数分，冲销与实际退款不同；余额由领域规则计算 |
| 工作与知识 | Goal、ArtifactVersion、EvidenceRef、DecisionRecord、MemoryEntry | 每项工作可验收，结论可回源，模型候选需确认后成为正式经验 |

每个聚合独立 streamVersion；关联引用同时携带对象 ID、版本和摘要。同一负责系统内的跨对象变更在同一事务和明确业务命令中完成，不能依靠前端顺序调用维持金额一致性。跨负责系统只使用版本化引用、动作回执和后续核对，不承诺共同事务。

合同与订单关系为一个合同可有多个订单；一个订单对应一个履约项目，项目具有多个里程碑、交付和付款期。首期不做跨订单收入分摊。费用可归集项目，成本缺失时不展示毛利。收款分配到订单付款期，超额金额进入待分配，不静默抵扣其他订单。

基础业务权限使用角色与对象范围共同判断。管理员管理配置，不自动取得财务批准权。销售人员访问本人或明确共享客户；销售经理访问所辖团队；项目负责人访问所管项目；财务管理获准订单的资金记录；审计员只读证据。价格、成本、联系方式作为独立字段权限，API、检索和导出均应用过滤。

正式报价、合同/订单生效、金额调整、客户验收、到账和退款登记始终要求有资格人员确认或读取已核验的外部系统事实。Agent 只能提出这些事实的候选，不能自证发生。

### 4.2 两种模式的责任划分

内置模式使用 business 插件作为业务提供方。连接模式用 Sales 提供客户、商机、服务价格、报价、合同/订单、付款计划和收支记录，Muniu 提供项目执行、任务、成果和经营协调。Muniu 的交付记录关联外部订单；同步给 Sales 的交付摘要不改变其订单或回款事实。

每个工作区保存版本化 ProviderBinding，按对象类型明确负责系统及允许写入能力，禁止同一种对象在两个系统同时可编辑。首期模式在初始化时选择；不提供带业务数据的在线模式切换。

ExternalObjectRef 必须包含 tenant、provider、objectType、objectId、sourceVersion、digest、observedAt 和权限引用。外部快照属于有来源的观察事实，不能因缓存更新而取得业务权威。来源过期或无法确认当前权限时阻止相关写入，历史展示标明采集时间。

连接器统一提供 readSnapshot、listChanges、prepareAction、executeAction、getReceipt 五种端口；未实现的能力显式声明不支持。版本使用提供方原始版本，不能用本地时间代替。

首期允许外部写入的动作仅为创建跟进任务、更新跟进日期和正式报价出包。跟进动作可以由限定策略预授权；正式报价出包须同时满足 Sales 业务批准与 Muniu 精确执行批准。同一有资格人员可在一个页面完成两项决定，后台分别记录，避免重复输入。

Sales 命令以稳定 operationKey 去重并持久保存回执；响应丢失后先核对原操作。Muniu 不直接写 Sales 数据库，也不承诺跨两个数据库的分布式原子事务。未知结果必须保留原操作和预算预留，重新授权不能生成新操作绕过未知状态。

所有影响 Sales 权威对象的动作都由 Sales 在自身事务中重验原对象版本与业务权限。Muniu 项目事实记录当时引用的外部订单版本，不表示外部订单同时发生变更。订单取消、金额或范围变化到达后，暂停受影响的未执行工作并形成差异待办，已交付或已发送事实不回滚。初始读取到命令提交之间的版本竞争必须作为 C01 场景覆盖。

连接模式下，涉及合同、订单金额或付款期的 ChangeRequest 先处于待外部办理，由人员在 Sales 完成批准与变更。Muniu 读取并核验其新版本后进入待项目确认，由项目负责人确认对应范围和里程碑后完成。期间显示待同步；引用版本不一致时进入冲突，禁止继续依赖旧范围的未执行节点。首期不增加订单修改的自动外部动作，也不把本地变更单的创建显示为两端业务均已生效。

## 5. 动态 Agent 协作与持续经营

### 5.1 统一执行概念

| 概念 | 定义与持久状态 |
| --- | --- |
| OperatingObjective | 企业某周期的经营目标；通过业务事实观察进展 |
| Goal | 一次范围明确、具有交付项和验收条件的工作，可由人或已授权规则提出 |
| OperatingPolicy | 持续任务规则、来源范围、模式、触发条件、有效期、预算及通知要求 |
| Authority/Mandate | 使用一个执行授权聚合；Mandate 表示其中不可变的授权版本，不增加第二套权限判定系统 |
| PlanRevision | 不可变任务图，固定能力、模型、输入、预算、依赖及验收条件 |
| Execution/Attempt | 一个节点的一次执行尝试；Job、租约和 generation 共同防止陈旧执行提交 |
| Trigger/Subscription | 来源事件和工作关联，决定哪些后续事实送入哪项工作；订阅不授予权限 |
| AttentionItem | 人员待办，关联确定的审批、问题、冲突或未知结果，不单独维护业务状态 |

Goal 的状态为草稿、待授权、执行中、等待人员、等待外部变化、待验收、待核对、已完成、失败、已取消。状态从已提交事件推导；必要业务动作存在未知外部效果时不得显示已取消或已完成。普通状态通知以独立投递记录呈现，不与业务完成状态混合。

### 5.2 接收与路由

来源包括 Web/CLI 明确请求、企业微信单聊及群内明确请求、内部业务事件、Sales 增量变化和持久定时事件。首期不监听全部员工聊天，不采集客户私聊历史，不启用会话存档或客户自动群发。

接收链先完成来源验证、租户定位、去重、回环过滤和权限检查，再由模型判断是否形成工作。稳定去重键由租户、来源实例、来源事件 ID 与类型组成。相同主题在评估中到来的事件合并为下一批；取消和撤权命令优先处理，不被普通批处理延迟。

新工作必须来自有权人员或启用的 OperatingPolicy。无法识别的发送者只形成隔离记录，不能启动任务。明确对象标识用于关联；模型可以建议合并，但不能仅因标题相近合并两个客户或两个授权事项。

每条持续规则固定 responsiblePrincipalId，执行 Agent 使用该负责人的当前授权与规则范围交集。负责人停用、移除或失去业务权限时，规则立即暂停并停止新增外部工作；已有未知动作继续内部核对，不向失权人员返回内容。接任人员必须显式接受责任并发布新授权版本，不能只更换显示姓名。规则创建者与负责人可以不同，但创建者不能代替负责人扩大权限。

来源游标与事件接收原子保存。Sales 先采用持久增量游标轮询；固定五分钟一轮，失败保留游标并退避。无事件变化时不调用模型。定时任务每分钟检查到期条件，用持久周期键防止多副本重复触发。

### 5.3 动态计划

协调 Agent 可以读取获准事实、提出任务图和改动理由。确定性规划校验器检查无环依赖、可用能力、模型额度、资料权限、业务权限、并发和累计预算，校验成功后才提交计划与派发意图。

授权内自动调整限定为：替换允许清单内模型/能力、重排未执行节点、增加必要的只读分析或成果整理节点、在剩余额度内重试已知无副作用的失败。新增外发目的地、客户/项目范围、可写字段、财务承诺、预算上限或交付目标时进入待授权。

计划替换只影响未开始的节点；保留原计划、执行中尝试及已验收成果。已开始动作不能被新计划重复安排。受影响的旧批准失效，来源版本变化后重新准备候选。计划提交和就绪 Job 创建使用同一事务，计算结果在提交时重验授权与当前版本。

Worker 不直接创建子 Worker；它提交拆解请求，由同一协调服务校验并纳入任务图。协调模型上下文按租户、工作区与资料权限隔离；默认只持有任务摘要和授权可见索引，详细资料按需读取，不能将全公司资料塞入一个长期会话。

建议初始配额：每项工作最多 6 个并行节点、32 个累计节点、64 次累计尝试、3 次自动重规划；每租户最多 20 个执行中节点。它们是可调的服务端上限，不是业务模型限制，提升上限需通过容量检查。任务必须有期限、token 和费用上限；管理员未配置有效额度时不执行模型工作。

路由、评估、复核、监督和摘要的用量计入同一租户及工作预算。节点不能各自重复领取完整额度。费用未知保留预留；无法可靠计量的外部 CLI 不进入托管自动执行流程，保留显式本地研发用途并显示其限制。

Goal 创建前的模型评估以持久 EvaluationAttempt 为计量单位，先从租户的独立入站评估日额度和单次上限预留，再调用模型。未接单或观察模式的费用仍结算到来源与规则；接单后将计量引用关联 Goal，不再次扣取已发生费用。没有评估额度、来源授权或有效责任主体时，程序保留事件并显示未评估，不调用模型。

### 5.4 监督、等待和停止

等待人员或外部事件时释放 Worker 执行槽位。监督先检查租约、心跳、待办、回执和成果变化；执行中节点连续十五分钟没有持久进展时，允许一次预算内只读诊断。诊断最多提出重规划建议，不修改权限、不执行补偿或直接重放工具。

暂停阻止新派发和新的外部写入；停止保存取消意图，并尽力中断已运行工具。已有在途请求可能仍完成，必须通过回执或人工核对结算。关闭规则后不再产生新任务，已接收任务按其授权和用户选择继续或取消，不静默丢弃。

租户公平队列为人工回应和取消保留调度优先级。普通任务不能占满全部容量使审批回应无法处理。连接器重连、模型限流和普通只读错误可退避重试；副作用结果未知禁止自动重试。

## 6. 授权、审批与信息处理

| 动作类别 | 默认规则 | 执行前需要绑定 |
| --- | --- | --- |
| 观察评估 | 管理员启用后分析候选，不启动主动工作 | 来源范围、评估预算、有效期 |
| 读取与草稿 | 已授权工作内可自动执行 | 当前成员、资料权限、允许模型和预算 |
| 内部低风险写入 | 明确规则授权后可执行 | 对象范围、允许字段、次数上限和数据版本 |
| 客户外发或正式业务动作 | 每次批准精确动作；首期客户外发仅生成草稿和人工发送记录 | 收件范围、正文/文件摘要、业务批准、版本和有效期 |
| 内部状态通知 | 管理员对固定渠道、接收范围和无敏感正文模板预授权后自动投递 | 通知策略版本、当前目的地权限、频率和稳定投递键 |
| 资金划转、法律签署、权限提升 | 本轮不提供自动执行能力 | 交由人员在对应系统办理 |

业务批准回答内容是否可正式采用，执行批准回答哪一个具体动作可以发生。两者权限和证据分别保存，允许同一合格审批人在一个页面明确提交两项决定，但该人不得同时是该高影响业务的制单人。正式报价、合同/订单生效、金额调整、客户验收、到账与退款登记均执行制单与批准职责分离；试点也使用两个具备独立职责的账号验证。Agent 制单时，制单责任归发起工作或持续规则的负责人员，不能通过换成 Agent 身份绕过职责分离。

执行权限等于人员当前对象权限、Agent 职责能力、连接器权限、授权版本和租户策略的交集。模型输出的 approved、已到账、已验收等文字不能作为授权或事实。每次派发、模型上下文读取、工具准入、结果外发和恢复均重验。

企业微信审批链接只用于定位待办，不携带可直接批准的令牌。登录后重新检查身份、当前对象版本与精确动作摘要。旧卡片和旧链接不能批准已变化的动作。群内只发不泄露客户、金额或原始内容的提示，详细结果在权限检查后的工作台读取。

普通状态通知不属于业务 Goal 的必需成果，发送未知或失败进入独立通知待核对列表，不能标为已送达，也不撤销已完成的业务验收。若用户将投递本身列为验收条件，则该动作纳入 Goal 的必要步骤；未核实送达前不能完成。两类发送都不得以更换投递键绕过未知结果。

知识采用原始资料、业务事实、人员决定和候选经验四类来源。读取、检索、摘要、导出均传播原始来源保护；来源撤销后阻止后续读取和传播。引用必须能定位到页码、段落或单元格。经验和流程发布为不可变版本，模型只能提交候选，管理员决定启用或回退。

企业配置只允许受控字段、阶段、指标和审批 schema。生命周期可设置显示和阶段准入，但不能覆盖金额、不变量、权限或必需沙箱。配置先校验、预览、测试，再由有权人员发布。

## 7. 公共接口与数据流

### 7.1 契约范围

在 packages/contracts 定义本轮新契约，API schema 是唯一生成源。沿用 `/v2` 作为项目路由约定，不表示保留旧接口语义。所有业务写入需要 Idempotency-Key，已有聚合更新需要 expectedStreamVersion。幂等回放也检查当前读取权限。

| 接口族 | 操作与用途 |
| --- | --- |
| `/v2/organizations`、`/v2/workspaces` | 企业开通、成员、部门、角色、对象授权、配额和模式配置 |
| `/v2/workspaces/{id}/business/{collection}` | 类型明确的业务对象查询与创建；collection 仅取发布的对象集合 |
| `/v2/workspaces/{id}/business/{collection}/{objectId}/commands` | 版本化业务命令，schema 按对象与命令穷举；不接受任意字段执行代码 |
| `/v2/workspaces/{id}/objectives`、`/v2/workspaces/{id}/reviews` | 经营目标、指标快照和周期复盘 |
| `/v2/workspaces/{id}/goals`、`/v2/goals/{id}/plan-revisions`、`/v2/goals/{id}/commands` | 工作、动态计划、授权、启动、暂停、恢复与停止 |
| `/v2/workspaces/{id}/operating-policies`、`/v2/workspaces/{id}/triggers` | 持续规则、接收事件、观察记录及启动依据 |
| `/v2/workspaces/{id}/attention`、`/v2/approvals/{id}/decisions` | 人员待办与精确批准/拒绝 |
| `/v2/workspaces/{id}/connections`、`/v2/actions/{id}`、`/v2/actions/{id}/reconciliation` | 连接、动作预览、回执和人工核对 |
| `/v2/workspaces/{id}/artifacts`、`/v2/workspaces/{id}/knowledge` | 受保护成果、来源、检索与导出 |
| `/v2/events` | 授权过滤后的 SSE，断线以服务器游标恢复 |

认证回调使用 `/v2/auth/*` 协议专用端点，以 state、nonce、PKCE 和单次回调凭据约束；它们不接受业务命令。企业微信首期长连接没有公网消息回调接口。对接层将来源事件转换为带稳定幂等键的内部接收命令，不要求外部厂商添加 Muniu 专用请求头。

主要新增类型为 BusinessObjectRef、ProviderBinding、OperatingObjective、OperatingPolicy、SourceTrigger、AuthorityRevision、PlanRevision、TaskNode、ActionIntent、ActionReceipt、AttentionItem、EvidenceRef。每个类型必须在 E0 附最小正例、撤权反例、过期版本反例和所属事件；实现不能只交付类型空壳。

### 7.2 一条完整数据流

员工在企业微信提出“检查本周到期项目和回款”。接入层保存来源事件并识别当前成员；协调服务从已授权对象中读取快照，形成交付检查与应收分析节点；确定性校验通过后提交计划、预算及 Job。Worker 生成带来源的风险清单和跟进候选，复核节点检查引用和金额口径。内部跟进任务按授权写入负责系统；正式业务动作进入待我处理。结果与回执写入事件，再更新总览并按通知策略回到原渠道。

如果员工被移除、订单版本改变或模型费用不明，后续步骤停在对应的撤权、过期或核对状态，保留已发生事实。此流程必须在内置模式和 Sales 模式使用同一组业务验收断言。

## 8. 企业微信和 Sales 实施要求

企业微信采用管理员显式配置的智能机器人长连接，每个租户的机器人凭据隔离保存。每个机器人只有一个持有效租约的接入实例，多副本通过租约接管。凭据轮换、失联、重复消息、断线期间的消息缺口均可见；不假定厂商会补发全部断线消息。

消息快速确认与长任务完成分开。短期流式窗口结束前转为工作台状态链接，不让执行依赖聊天窗口持续存在；通知发送失败保留待投递记录，发送前再次检查权限和原目的地。对于无法核对结果的发送超时，进入待核对，不盲目重发。

Sales 主仓库 `8913a94c567403bd2f3021d09b0bf9474bd4102d` 作为客户、商机、订单和收支规则的审查起点；RFQ 工作树 `4dc5cceafbb5288e86698c57e9e22de5b5dd6eb9` 作为受控报价出包、回执和恢复实现的候选来源。实施时在 Sales 专用工作树按实际差异选取代码，不能将两个工作树都视为最新主线或直接整体合并。

Sales 保持独立构建和 TypeScript 5.9.3，Muniu 保持 5.7.2，通过版本化 HTTP 契约互通。合同、项目服务和付款计划若当前 Sales 不完整，在本计划的 Sales 工作包补齐，不能用固定假数据宣布连接模式完成。

端到端使用一个已核验登录主体及服务端显式映射，消除在页面手动粘贴另一个系统 Bearer token 的交互。服务间使用短期、受众限定的身份和凭据引用，业务端仍检查实际人员的当前权限，不能由服务账号拥有全部业务权限。

## 10. 测试矩阵与发布门槛

### 10.1 必须通过的行为场景

| 编号 | 场景 | 判定 |

| B01 | 报价、客户接受、合同与订单、交付、验收、回款 | 每个事实独立有依据，金额守恒；两模式相同业务输入得到相同口径结果 |

| B03 | 多人并发与审批后对象变化 | 冲突可见，旧批准失效；不覆盖他人变更 |
| A01 | 跨租户、跨客户、字段权限和敏感群回复 | API、搜索、导出、SSE 和模型上下文均不泄露 |
| A02 | 排队、模型在途、准备动作、批准后、恢复时撤权及规则负责人离职 | 后续受控动作全部拒绝，规则暂停，接任重新授权；已在途效果单独核对 |
| A03 | 文档注入、冒充领导、伪造模型批准、伪造来源身份 | 不产生新增权限或交易事实 |
| R01 | 重复、乱序、迟到事件和回环 | 稳定去重，游标正确，历史复盘不被暗改 |
| R02 | 计划替换、取消、Worker 租约过期和旧结果到达 | 无重复动作，陈旧 generation/fencing 被拒绝 |

| R05 | PG、CAS、KMS 联合恢复、部分丢失和窗口内已发生的外部动作 | 恢复后默认隔离；潜在丢失的承诺和回执完成外部核对前，不回放来源或恢复外部写入 |
| P01 | 接单前评估、规则关闭、到期、费用不明、配额耗尽、无限拆解 | 入站评估先预留且不重复扣费；不再派发，不超授权，未知费用保留预留 |
| P02 | 长时间等待、人工回应与大量普通任务竞争 | 等待不占槽位，人工回应可优先处理，租户之间不饿死 |
| K01 | 来源撤回、候选经验、流程版本更新 | 撤权阻止传播，在途版本不被静默替换 |
| C01 | Sales 权限/版本变化、游标断点、联合身份、回执超时 | 两端分别授权，原操作唯一，不依赖共享数据库事务 |
| C02 | 企业微信多副本、断线、重复消息、密钥轮换和旧审批链接 | 单活动接入、缺口可见、旧凭据失效、批准重新验证 |
| U01 | 首次使用、业务主流程、重连、失败与核对 | 浏览器可独立完成；Desktop/CLI 状态与权限一致 |

### 10.2 模型与业务效果

每种模式至少 30 个代表性任务，其中 20 个用于调试、10 个独立留出，留出集每条流程至少两项，覆盖缺失资料、冲突和失败。每个任务在同一冻结配置下执行三轮。另有不少于 20 个安全与恢复任务；安全样本全部要求通过，不与业务平均分抵消。

通过条件：业务任务首次验收率不低于人工基线；包含审核、纠错和返工在内的人工总耗时至少下降 20%；金额规则、权限和事实来源等程序必检项全部通过。每种流程分别报告，不只报告总平均值。记录模型版本、输入范围、全部费用、人工时间和失败原因，禁止只挑成功样本。

发布成绩只使用冻结留出集，调试集单独报告。人工基线使用同一输入、权限、验收量表和可用业务工具，由人员独立完成一次并接受同一复核。首次验收率按全部三轮首次提交计分；人工耗时先对每项 Agent 任务三轮取平均，再汇总与对应人工基线比较，失败和返工时间均计入。按模式分别达到门槛，报告每流程分项及波动，不将重复运行当成新增独立样本。量表、计时点、暂停等待处理和复核人员在 E0.2 冻结，评测后不得改口径来提高成绩。

观察模式至少运行十个工作日，累计审阅至少 100 个主动候选；建议动作准确率至少 90%，越权动作零容忍，之后由管理员逐条策略启用自动执行。样本不足则维持观察。跟踪首次验收率、每项已验收成果成本、无效提醒率、人员等待时间和实际业务进展，不以 Agent 数量或 token 消耗作为价值指标。

以上数字是本轮拟采用的验收目标，不是现有实测结论。真实客户试点前需要取得数据使用与模型处理范围授权；没有真实客户证据时，只能标记工程候选通过。

### 10.3 容量与运行目标

首期容量测试目标为 10 个租户、每租户 200 个成员、合计 100 个活跃浏览器连接、200 个已派发执行节点和每分钟 300 个输入事件。采用固定响应时间的模型替身测试平台容量，真实模型单独报告排队和推理耗时。

参考验收环境为 2 个 Host（各 2 vCPU/4 GiB）、2 个 Worker（各 4 vCPU/8 GiB）、2 个连接器实例和 PostgreSQL（4 vCPU/16 GiB），对象存储与 KMS 独立提供。固定数据量为每租户 1 万客户、2 万订单和 10 万历史事件，连续运行两小时，并注入上述故障。

在该环境下，非模型业务 API p95 不超过 800 ms，控制命令持久接收 p95 不超过 1 s，已提交变化到页面可见 p95 不超过 3 s；30 秒执行租约下，单 Worker 失效的可恢复任务在 60 秒内进入接管处理。模型限流不得造成权限校验或取消入口失效。

Host/Worker 故障后的已提交事件恢复目标为 RPO 0。整套存储灾备的建议目标为 RPO 不超过 15 分钟、RTO 不超过 4 小时，必须以 PG、对象和 KMS 的联合演练证明；不能仅由数据库备份频率推断达标。

允许存储丢失窗口不代表允许重放该窗口内的外部工作。灾备恢复默认进入隔离状态：关闭外部写入、自动派发和来源事件重新接单，保存恢复时间点与潜在丢失窗口。核对人员从 Sales 操作账本、渠道回执及获准外部审计中核验该窗口的已发生动作，恢复稳定操作标识与结果后，才按租户和连接器解除隔离。仅校验本地三类存储一致不能解除隔离。

连接器无法提供完整回执或无法证明窗口内没有副作用时，保持相关能力停用并人工处置，不推断为未执行。灾备测试必须包含“外部动作已成功，但本地承诺、operationKey 和回执都在恢复点后丢失”的情况。四小时 RTO 包含必要核对和业务恢复；只恢复服务进程或只读界面不算完整业务达标，不能证明时记录失败并调整恢复设计后重测。

## 12. 实施组织、节奏与发布

建议投入八个全职角色：技术负责人一名、后端三名、前端两名、测试一名、运维一名；业务负责人持续参与流程与验收。后端分别负责企业平台、Agent 执行、经营与连接，Sales 工作由经营与连接方向统筹。Agent 可辅助实现和测试，不能替代业务确认与独立审阅。

以该配置估算首个试点候选需要 16–20 周：第 1–2 周 E0，第 3–6 周 E1/E2/E3 与 E6.1，第 7–12 周 E4/E5/E6，第 13–16 周 E7，第 17–20 周试点观察和发布准备。该估算不代表上线承诺；环境、模型、真实客户与人员到位情况记入进度，不能降低门禁换取日期。

每周交付可运行的业务增量和证据，不按“代码量完成百分比”汇报。每个包只修改批准范围，合并前检查依赖与契约；多个 Agent 或工程师不得同时改同一契约源文件。接口变更通过契约负责人整合。

发布先部署全新预发布环境，以合成企业运行完整验收，再开通一家内置模式和一家 Sales 连接模式试点。主动规则先观察，再按规则启用受控执行；首期客户外发仍由人员办理。

生产准备使用不可变镜像和插件锁，至少双 Host/Worker。新版本先验证、再停止旧调度并排空或核对在途动作，切换同一锁版本的服务。首次正式上线前不兼容历史研发状态；正式运行后的数据库演进和运维恢复规则在发布门禁中建立，不能因本轮无需兼容而省略。

试点异常先停用相应规则、连接器或写入能力，保留记录和只读界面；未知动作未核对前不回退数据库来重复执行。代码回退只在数据库与事件格式匹配时进行，否则修复后前滚。运行告警覆盖授权拒绝异常、队列积压、未知回执、预算超限、来源滞后、KMS 失败和备份失败。

上线所需外部条件包括身份发行方、云账号与域名、企业微信管理员与测试机器人、Sales 测试环境、模型账号和额度、两类试点企业及获准资料。条件未齐时继续不依赖它们的工程工作，保留对应验收为未运行；不将临时测试身份用于生产。

## 13. 代码取舍与上游规则

本计划通过后用新 ADR 取代与目标设计冲突的单执行者、固定团队、OPC 工作区大聚合和历史数据升级安排；历史 ADR 保留并标记被取代，不能改写当时的验收结果。更新 AGENTS.md、架构、开发说明、状态页和契约生成器，使后续执行者只面对一套当前规则。

保留通用控制职责：Host 唯一组合根，产品插件不进入 Kernel，公共 SDK 边界、事件事实、工具策略、不可变批准、来源保护、未知结果不重放和 fail-closed 沙箱。算法和组件是否复用以新契约、测试与边界为准，不为保持目录或版本标签而保留旧代码。

PMTSoul 仅作产品与交互参考，不复制其代码。DeepSeek super-agent 本轮仅采用设计理念，默认由 Muniu 独立实现，不新增上游运行时依赖。现有适配只使用仓库已批准提交；若要复制或改编新原型，须单独审查确切提交、许可证和来源清单，不因批准总体设计而扩大许可范围。

没有执行旧数据迁移、状态清理、生产部署、公开发布或 npm 包发布的隐含任务。删除旧源码仅发生于本轮受控分支，须具备替代实现与验证；不删除用户业务文件、密钥或其他工作树。
