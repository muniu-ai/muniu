# Muniu 多 Agent、多模型复杂任务协作方案

建议把 Muniu 从持久 Agent 执行平台扩展为围绕目标持续组织工作的系统：用户定义结果和边界，平台维护计划、选择执行者、组织协作、验证成果，并在事实变化时调整后续工作。复用现有 Kernel、Agent Runtime、Worker、审批、预算和领域插件，优先补齐任务编排与交付验收。

本文是供评审的完整提案，不是已批准实施计划。研究日期为 2026-10-09；源码基准为 `main@0609e2a6fcfb1b9efae0fadf4039888d98df1166`。本轮仅新增方案与文档导航，没有修改生产行为、合并其他分支或发布产品。

用户已确认两个方向：覆盖软件研发与经营任务；同时支持模型 API、Codex、Claude Code 等独立 Agent。具体模型型号、金额限额和实施排期在相应子计划中确定。

## 2. 从书中观点到产品要求

以下是对上述三个核心章节的概括，不是原文摘录：系统需要围绕用户希望得到的结果持续组织工作；调度需要管理依赖、能力组合与执行中的变化；组织记忆需要保留判断依据和修订过程；资源调用与协作必须具有明确的授权范围。对应章节链接见上一节。

| 设计要求 | Muniu 应产生的具体行为 |
| --- | --- |
| 以目标作为入口 | 输入目标、交付物、约束和验收条件，系统生成可审阅计划 |
| 维护任务全过程 | 保存依赖、阻塞原因、执行尝试、结果版本和后续动作 |
| 按能力组合执行者 | 分别选择 Agent 职责、执行方式及模型，说明选择依据 |
| 根据新事实调整 | 生成新的计划修订，保留仍有效成果，明确作废范围 |
| 保存组织判断 | 记录已采用与放弃的方案、证据、适用条件和待核实假设 |
| 让经验改善后续任务 | 从验收结果形成评测样本、模板和待确认记忆，再验证改进效果 |

这些要求不意味着每个任务都要启动多个 Agent。并行调研适合拆分；高度耦合的修改通常需要串行推进。Anthropic 的工程经验也指出，多 Agent 会增加协调和 token 成本，适用性取决于任务的可分解程度。[多 Agent 研究系统实践](https://www.anthropic.com/engineering/multi-agent-research-system)

对 Muniu 的取舍是：通用平台提供一致的任务契约，首批以研发、机会研究两种工作流验证；先把结果质量和恢复机制做实，再扩展场景数量。

## 4. 目标架构与模块边界

建议采用确定性控制服务配合模型规划。模型提出计划和调整建议；代码验证依赖、权限、预算、状态与验收规则，并决定是否允许派发。

```text
用户目标 / 文件 / 已授权业务数据
                |
       Desktop / CLI / HTTP
                |
          Host（唯一组合根）
                |
   目标与计划服务 —— 能力目录与路由策略
                |
   调度准入 —— 预算 / 权限 / 配额 / 资源锁
                |
       持久 Execution + Job
          /             \
  Muniu 内部 Agent     外部 Agent Runner
  模型 API + 工具      Codex / Claude Code
          \             /
        版本化成果 + 证据 + 独立验收
                |
       用户接收 / 有界修订 / 经验提案

所有业务状态由 KernelEventV1 派生；SQLite / PostgreSQL / CAS
保存事实及受保护内容，查询投影和界面不另立事实源。
```

| 模块 | 建议职责 | 必须保持的边界 |
| --- | --- | --- |
| `packages/contracts` | 目标、计划、任务节点、委派、路由、成果与验收契约 | 先冻结 schema 和事件，不手改生成文件 |
| `packages/kernel` | 通用事件、权限、审批、预算承诺与状态校验 | 不引入 OPC/Coding 规则，不导入产品插件 |
| `packages/agent-runtime` | 节点生命周期、上下文、模型边界和 AgentHandle | 不保存另一套业务事实，不依赖 Shell |
| 建议新增私有 `packages/task-orchestration` | 通用计划校验、就绪计算、调度与汇合 | 名称及边界待 ADR；插件不能直接导入该私有包 |
| `packages/plugin-sdk` | 声明能力、提交候选结果、调用获准领域验收的公开端口 | 仅暴露经过批准的最小能力 |
| `apps/host` | 装配以上服务，提供 `/v2` 及统一授权入口 | 仍是唯一组合根 |
| `apps/worker` | 领取节点 Job、启动执行、提交结果、处理核对 | 复用租约与 fencing，不在内存 Promise 中充当唯一调度器 |
| OPC、Coding 等插件 | 领域任务模板、专业 Agent、成果结构和验收器 | 保留不可变事实和各领域人工决定 |
| Desktop、CLI | 展示目标、计划、执行、费用、问题与交付 | 共用 Host 契约，视图不改变业务规则 |

首版不更换 Cordis、不引入第二套工作流持久化引擎、不迁移早期协议。LangGraph 等框架可作为持久化和工作流模式的参考；若未来采用，只能先明确与现有事件、权限、恢复的职责关系。[LangGraph 持久化文档](https://docs.langchain.com/oss/javascript/langgraph/persistence)

## 5. 核心对象、状态与契约

以下名称和路径是拟议契约，尚不存在的部分不得当作可调用 API。

| 对象 | 最少需要保存的内容 |
| --- | --- |
| `Goal` | 用户结果、范围、交付清单、验收标准、负责人、期限、预算与数据策略 |
| `PlanRevision` | 不可变版本、父版本、节点和依赖、变更理由、用户授权引用 |
| `TaskNode` | 子目标、能力要求、输入引用、输出 schema、验收器、权限、额度、期限、冲突资源 |
| `TaskAttempt` | 节点与计划版本、Execution/Job、执行者快照、尝试序号、状态、租约代际 |
| `AgentDefinition` | 职责、版本、输入输出 schema、工具需求、支持环境、策略和评测版本 |
| `ExecutionTarget` | `managed_agent` 或 `external_runner` 的类型化配置快照 |
| `RouteDecision` | 候选集、淘汰原因、实际选择、策略版本、能力与价格快照 |
| `HandoffPackage` | 目标摘要、获准输入、来源和版本、产物要求、未决问题、权限及到期条件 |
| `ArtifactRevision` | Asset/CAS 引用、摘要、来源节点、输入版本、分类、授权和可见范围 |
| `AcceptanceRecord` | 标准版本、成果摘要、程序检查、语义复核、用户接收及未满足条款 |
| `ArtifactCarryForward` | 新计划版本、原节点与成果摘要、输入及标准比对、当前授权与沿用检查结果 |
| `DecisionRecord` | 决定、公开理由摘要、证据、放弃方案、适用假设与复核触发条件 |

Agent 是执行某种职责的配置与运行单元，模型是其推理服务，Runner 是外部执行程序。三者独立命名和版本化。不得把“研究员”永远绑定某个模型品牌，也不得把 Codex 当作普通模型端点。

目标状态建议为 `draft → ready → active → awaiting_acceptance → completed`，另有 `pausing / paused / blocked / cancelled / failed`。计划节点有 `pending / ready / running / awaiting_input / awaiting_approval / validating / accepted / invalidated / failed / cancelled / needs_reconciliation`。节点状态是新契约，不改写既有 Execution 的含义。

仅当所有必需交付项通过验收且满足接收政策，Goal 才能完成。模型结束回答、外部程序退出码为零、子节点全部返回，都不能单独证明目标已完成。非必需分支失败可交付带明确缺口的候选结果；降低原验收要求需要一次可审阅的目标修订。

拟议 HTTP 入口：

| 路径 | 用途 |
| --- | --- |
| `POST /v2/workspaces/:workspaceId/goals` | 创建目标 |
| `POST /v2/goals/:goalId/plan-revisions` | 保存候选计划或修订 |
| `POST /v2/goals/:goalId/commands` | 启动、暂停、恢复、取消及采纳修订 |
| `GET /v2/goals/:goalId` | 查询目标和当前可重建视图 |
| `GET /v2/goals/:goalId/tasks` | 查询节点、尝试及结果关系 |
| `POST /v2/goals/:goalId/acceptances` | 提交绑定成果版本的验收决定 |

所有变更要求 `Idempotency-Key`，更新已有聚合还要求 `expectedStreamVersion`。权限检查不能只依赖 URL 中的 ID；必须核对 tenant、workspace、对象授权和当前成员资格。沿用既有 SSE 机制，不新造第二种事件游标。

## 6. 规划、调度与有界重规划

### 6.1 先形成可执行计划

目标澄清只询问会改变结果、权限、预算或验收的问题。规划 Agent 输出结构化候选计划，校验器检查：无环依赖、节点数量与深度、输入可访问性、输出类型匹配、所需能力存在、期限可满足、权限可衰减、额度可预留以及每项交付物都有验收路径。

先提供三种执行模式：单 Agent、固定模板的依赖图、经过校验的动态计划。短任务默认单 Agent；多个方向可独立研究或确有不同能力需求时才拆分。模型无法给出合法计划时保留草稿并提出具体问题，不能直接执行生成的 JavaScript 工作流。

### 6.2 调度器的可验证规则

1. 从已提交事件重建当前计划，计算输入仍有效、前置节点已验收的就绪集合。
2. 按 tenant/workspace 公平分配额度，再依据用户优先级、等待时长和依赖路径选择节点；禁止高优先级目标永久饿死其他目标。
3. 检查执行者健康状态、数据出口、工具权限、预算、模型 RPM/TPM、Worker 容量和冲突资源。无可用执行者时说明原因并等待，不偷偷放宽限制。
4. 在同一事务内绑定计划版本、预留预算与资源、创建尝试和 Execution/Job；相同调度键只能成功一次。
5. Worker 开始时重新检查授权、计划有效性、身份和 fencing。外部工作前先持久化上下文及工具承诺。
6. 提交结果时检查尝试代际、所属计划版本、输入摘要、授权和成果摘要。迟到或被取消的结果保留审计，但不能直接推进当前目标；跨计划版本的有效成果须按第 6.3 节显式沿用。
7. 验收成功后释放可释放的预留和资源、生成后继就绪节点；失败按有限修订政策处理。

父任务等待子节点时释放 Worker，不长时间占住一个执行线程。调度器按持久事件唤醒；进程内消息只是加速信号。节点完成与唤醒意图通过 outbox 原子提交，避免“子任务已完成、父任务永远等不到”。

建议首版默认每目标最多 3 个并行节点、1 层委派、2 次自动重规划；这些是待压测的保守默认值，不能覆盖工作区更严格的上限。总节点、总尝试、期限及 Muniu 可控制的资源设准入上限，创建子任务不会重置。外部 Agent 内部 token、工具次数和费用只能按经过验证的能力限额；不可观测项目不得声明硬上限。

共享同一源文件或业务聚合的写入串行化。研究分支可并行；代码分支各用独立候选副本，再由集成步骤合并并重新运行 Gate。资源锁按规范顺序申请，冲突节点回队列，防止死锁；锁失效或 Worker 丢失后先检查未知副作用，不能仅凭超时把相同写入派给别人。

### 6.3 在明确的边界调整计划

新证据、用户 steer、验收失败、执行者不可用或预算不足可触发重新规划。协调者产生差异：新增/删除的节点、受影响成果、剩余额度、风险和理由。系统只保留输入与验收条件均未改变的已验收成果。

计划修订提交后，旧版未派发节点失效；正在执行的受影响节点收到取消或中断请求，其结果归入旧版。新计划要使用已验收的旧成果，必须追加 `ArtifactCarryForward`，绑定原成果摘要、新计划版本、相同输入与验收条件，以及当前有效授权的核验结果。没有该记录的旧成果不能解锁新计划节点。

未受影响且仍在运行的尝试继续绑定旧计划，禁止悄悄改绑。它完成后先按旧版本提交候选，再经过同一沿用检查才能进入新计划；期间新计划不得另起重复节点。沿用只采纳成果，不继承过期的工具批准。授权、输入、验收条件或执行配置发生实质变化时重新验证或重做。

仍在原授权范围和预算内的调整可按用户已选择的政策继续；增加权限、改数据接收方、扩大承诺或超预算需要用户决定。

研究中的循环以“新节点/新尝试＋新计划修订”表达，图本身仍无环。Coding 原有最多三次自动修复的累计限制继续有效；通用重规划不能绕过该限制。没有新的可操作证据、重复同一失败或达到上限时停止自动尝试，并展示已经得到的结果。

### 6.4 持续任务与事件唤醒

对于需要持续数周的研究或经营目标，另设用户明确启用的跟进订阅，保存触发来源、检查频率、有效期、终止条件、数据授权和每周期额度。优先使用业务事件与有界定时检查；没有变化时不反复调用模型，只在变化达到规则阈值后生成待处理任务。

触发记录有稳定去重键。暂停订阅阻止新任务；撤销数据权限、目标关闭或订阅到期使订阅失效。提醒聚合同一事项，只在出现实质变化、失败或需要用户决定时通知。跟进不会自动获得原目标之外的联系客户、付款或发布权限。

每次唤醒创建新的 Execution，关联同一长期目标及既有决策。旧 Execution 的期限与用量不重置，目标的累计费用也不清零；新增周期额度必须已在订阅策略中明确授权。一次交付可以完成，后续监测作为独立、可停止的跟进目标存在，避免“长期运行”让任务永远无法验收。

## 7. Agent 目录与多模型路由

### 7.1 首批角色

| 职责 | 主要输出 | 选择方式 |
| --- | --- | --- |
| 协调与规划 | 目标解释、依赖图、差异计划 | 擅长结构化规划和复杂约束的已评测模型 |
| 研究与取证 | 带来源、时间及反证的发现 | 内部 Agent 调用受控检索工具 |
| 提取与整理 | 符合 schema 的结构化材料 | 满足准确性要求的较低成本模型 |
| 研发执行 | 候选代码、变更说明和检查材料 | 内置 Coding、Codex 或 Claude Code |
| 经营分析与写作 | 决策档案、草案、假设和待验证项 | 匹配领域模板的内部 Agent；外部 Agent 作为可选委托 |
| 独立复核 | 对照要求的缺陷和证据检查 | 与生成步骤隔离上下文，必要时使用不同模型 |
| 确定性验证 | 测试、schema、摘要、数值和来源规则结果 | 普通程序或领域 Gate，无需模型 |

这是能力分类，不要求每个目标都启动七个 Agent。复核者应获得需求、成果和证据，默认不接受生成者的自评分作为判断依据；使用不同厂商也不等于推理错误相互独立。

### 7.2 模型连接与模型配置分离

`ModelConnection` 只负责凭据、厂商和端点；`ModelProfile` 保存模型 ID、支持的输入/输出、上下文限制、工具与结构化输出能力、部署区域、价格来源日期和评测版本；`RoutingPolicy` 表达选择规则；`RouteDecision` 保存每次实际选择。

先进行硬过滤：数据是否可以发送、能力是否满足、上下文及输出额度是否足够、价格是否有效、预算是否可预留、配额和服务是否可用。再按任务类别的评测结果选择质量、时延与费用的合适组合。质量未知的配置只进入受控试验，不作为生产自动候选。

首版提供“自动选择、优先质量、控制费用、固定配置”四种策略。控制费用仍须达到质量下限。建议采用可解释规则及顺序比较，先不引入未经校准的加权总分或在线学习算法。

模型 ID、参数、连接、工具 schema、Agent 版本和价目表在一次尝试中固定；厂商若只能提供浮动别名，记录返回的实际版本信息及可复现性限制，不能承诺严格复现。模型切换发生在已知安全的尝试边界，重新生成路由记录和上下文快照。

未指定当前“最强”或“最便宜”的型号。接入子计划以实际可用账户和一组代表性任务做对比，再冻结型号与参数。现有仓库价格参考日期不能当作 2026-10-09 的最新报价。

### 7.3 故障处理与降级

| 观察到的情况 | 允许行为 |
| --- | --- |
| 调用前发现配置不可用，确认未发送 | 按授权候选集改选，并记录原因 |
| 厂商明确拒绝且确认未执行，例如可判定的配额拒绝 | 有界退避或改选，重新检查额度 |
| 结果完整但验收不通过 | 保留结果；在修复额度内新建尝试，必要时升级模型 |
| 请求已发送，响应、费用或工具结果未知 | 保留预留，暂停受影响路径并核对，不通过换模型规避 |
| 没有符合数据或沙箱政策的候选 | 阻塞并说明缺少的能力，不回退到更宽权限 |

OpenAI 的评测指导也将路由与交接列为多 Agent 系统新增的误差来源。评测应决定是否需要拆分及切换，不能仅凭角色设计推断收益。[评测指南](https://developers.openai.com/api/docs/guides/evaluation-best-practices)

## 8. 独立 Agent 的接入与治理

### 8.1 两种执行方式共用交付契约

| 项目 | Muniu 内部 Agent | Codex、Claude Code 等外部 Agent |
| --- | --- | --- |
| 推理循环与工具派发 | Muniu 控制 | 外部程序控制 |
| 模型与凭据 | Muniu BYOK 和路由 | 外部配置与账户 |
| 上下文 | Muniu 保存完整可见请求 | Muniu 保存委托包和收到的事件，不宣称知道全部内部上下文 |
| 审批 | 中央策略逐次检查工具 | 当前主要审批 Runner 启动与产物采纳 |
| 费用 | 按用量和参考价预留结算 | 仅在可靠回报时记录，否则标记未提供/待核对 |
| 恢复 | 事件、检查点与工具承诺 | 还必须核对外部会话、进程和实际成果 |
| 最终完成条件 | 通过 Muniu 验收 | 同样通过 Muniu 验收 |

现有外部 CLI 在 macOS 候选仓库中运行，沙箱限制写入范围，但允许文件读取和外部网络。它不是严格数据隔离环境。企业 Kubernetes 路径当前仅支持 builtin。新增调度界面必须准确显示这一区别，不能把启动审批宣传为对外部 Agent 内部工具的逐项治理。

### 8.2 第一阶段：明确授权的委托执行

用户在工作区确认 Runner 二进制真实路径、版本、摘要、账户和控制范围，再选择允许参与该目标的 Runner 集合。该选择需要记录在目标策略中；默认保留当前显式选择方式，不因某个模型失败就静默改用外部 Agent。

统一委托包包含任务 ID、目标、允许输入、期限、结果 schema、成果目录及验收条件。每个尝试有独立候选目录；不让两个外部 Agent 共写源仓库。Muniu 验证其产物路径、摘要和内容结构，防止路径穿越、符号链接及超范围读写的产物被采纳。

不要改写外部程序的全局 Prompt、Skill、MCP、模型连接或历史会话，不把 Muniu 密钥注入外部账户。协调 Agent 若需要模型，使用独立 Execution 和预算；外部执行节点不再伪装成必须使用某个 Muniu 模型连接。

受信模式只接收用户明确允许交给该程序的资料。若目标要求“只能访问指定文件”或“禁止向其他端点发送数据”，当前模式应判为不满足条件，不能仅靠任务文字声称满足。对外发送、合同、发布及付款应由 Muniu 获准工具完成；这是一项产品分工，不构成现有受信 Runner 无法自行联网的技术保证。

### 8.3 第二阶段：受限执行配置与审批桥接

新增独立的 Runner 配置，验证进程环境、只读输入挂载、文件范围、网络出口、短期凭据、子进程、撤权和取消行为。只有测试证明满足某项隔离要求，能力目录才可以声明该能力。

Codex 非交互模式适合有界任务及结构化事件；需要持久交互和客户端审批时，可另评估 App Server Adapter。Claude Code 可通过官方 CLI 提供程序化调用、事件和指定会话恢复。具体参数按准入版本验证，不把厂商接口能力当作 Muniu 已集成能力。[Codex 非交互模式](https://developers.openai.com/codex/noninteractive)、[Codex App Server](https://developers.openai.com/codex/app-server)、[Claude Code 程序化运行](https://code.claude.com/docs/en/headless)

Claude Code 的费用限制存在客户端估计和跨恢复轮次的边界；即便启用，也不能代替 Muniu 的累计记录或承诺精确封顶。[Claude Code CLI 参考](https://code.claude.com/docs/en/cli-reference)

适配器必须声明支持的控制粒度、结构化事件、可验证取消、会话恢复和费用回报能力。不支持的字段标记 unknown，不填默认成功。不采用 ACP，不导入仓库排除的 Claude SDK payload；需要改变当前自治边界时单独提交 ADR 与验收计划。

## 9. 上下文、记忆与安全

### 9.1 用交接包共享必要信息

每个节点只接收完成任务所需的材料：目标和限制、已验收前置成果、相关决策、原始来源引用、未决问题及产物要求。大型内容使用受保护 Asset 引用，按授权读取，避免把所有对话拼给每个 Agent。

交接包保留来源事件、内容摘要、产生时间、有效期、数据分类、授权与计划版本。摘要是辅助视图，不能替代原始证据；冲突信息分别保留，不能由摘要模型静默合并。输入材料、网页与外部 Agent 输出均视为不可信内容，不能改变工具权限或系统指令。

模型请求前检查 token 与上下文预算。优先删去无关材料，再对可压缩部分生成带原文引用的摘要；不得压掉验收标准、关键反证、未完成工具承诺或授权边界。保存实际发送的上下文，供恢复和审计。

### 9.2 区分三种长期资产

| 资产 | 保存什么 | 进入下一任务的条件 |
| --- | --- | --- |
| 任务记录 | 事件、输入输出、决策、版本和检查结果 | 有效授权与保留政策 |
| 记忆 | 已确认偏好、业务事实和适用经验 | 用户接受、未过期、共享授权仍有效 |
| 模板与技能 | 可复用流程和方法 | 独立版本、评测和发布流程 |

完成任务后可生成记忆提案，不自动把模型推断升级为组织事实。持续学习先优化模板、提示和路由规则，不默认上传客户材料训练模型。保存可供审阅的理由摘要与证据即可，不要求提取模型隐藏思维过程。

跨插件共享继续使用 share grant。撤销权限后停止后续读取和派发，使依赖成果失效并提示重新生成；已发送到外部服务的数据无法召回，应在授权界面说明。内容删除继续遵守独立密钥销毁、tombstone 和历史完整性规则。

### 9.3 控制范围必须覆盖协作链

内部父子 Agent 的工具、数据、额度与深度只能衰减；外部 Runner 只接收能力声明能够执行的委托范围，不声称其未知的内部调用同样受控。中央工具策略仍检查经 Muniu 派发的工具 effect class、参数和资源摘要。新增计划、换模型、换 Runner 或调整参数不能继承不再匹配的批准。

生产插件继续属于进程等价可信代码，签名和完整性不等于沙箱。HMR 只在显式开发配置启用。缺少所需 sandbox 时拒绝执行，不采用无隔离回退。遥测默认关闭；日志和评测样本脱敏，不能把业务原文塞入公开事件或 trace 标签。

## 10. 费用、配额与资源管理

目标持有按币种划分的额度，例如分别设置 USD 与 CNY 上限；子 Execution 仍可使用单币种预算，父级聚合多个子额度。首先设计目标预算预留与现有模型预留的映射，避免同一额度同时被两个层级重复计算或释放。

准入时，每种币种的已结算费用与尚未结算的占用之和不得超过授权额度。占用只计算一次：父级给子执行保留的额度已经包含子执行内部模型预留，不能再次相加；结算时将对应占用转为实际费用，仅释放已确认不用的余额。

内部调用先预留后发送，结算仅一次。若厂商报告的实际费用超过预留，仍完整记账并进入超限状态，停止后续付费派发；不能因超过授权上限而拒记真实费用，也不能宣称最终账单绝不会超过估计。

建议为目标预分配执行、复核和修复额度，例如 65%、20%、15%。比例只是初始配置，必须随任务类型评测；不把所有预算都分给生成步骤。费用未知的请求继续占用预留，重启、resume 或重新规划不得释放未知消耗。

外部 Agent 单列：已报告用量、参考估计、不可观测费用和账户侧约束。无法获得可靠费用的 Runner 不能满足“必须在精确金额内自动停止”的目标。内部 Agent 的预留控制也不等于厂商账单精确封顶；这种要求只有在厂商与适配器均提供可验证保障时才可接受，否则说明限制，由用户调整约束。

统一显示金额时仅作估算，注明汇率来源、日期与原币种，不拿隐式换算替代币种准入额度。内部 token、工具次数以及平台管理的并发、节点数和外部进程数分别限额。外部程序内部消耗只有经过验证的报告与控制接口才能纳入对应限制；目标要求其不支持的硬限时，拒绝选择该 Runner。期限到达触发停止请求，未能证明进程已停时保留核对状态，不能把“已发送取消”当作严格停止。工作区配额不足时排队并显示等待原因。

任务总期限在暂停、等待批准和重启后仍持续计时。等待配额消耗期限但不重复占用 Worker；确需延长期限或费用，创建新的授权记录，不重置历史消耗。

## 11. 故障恢复与取消

目标执行不承诺外部副作用的全局 exactly-once。沿用至少一次 Job 投递、内部幂等提交与未知结果人工核对，保证不会因恢复而擅自重放未知外部动作。

| 故障点 | 要求的行为 |
| --- | --- |
| 派发事务提交前崩溃 | 没有外部工作；重算就绪集合，使用稳定调度键 |
| Job 已提交、尚未领取 | 其他 Worker 可按正常租约领取 |
| 子节点已完成、父任务尚未更新 | 从提交结果与 outbox 恢复汇合，不重跑子节点 |
| 租约失效、旧 Worker 迟到提交 | fencing 拒绝提交，不采纳旧结果 |
| 模型请求已发送但结果或费用未知 | 冻结对应额度并核对；不自动换模型重发 |
| 外部 CLI 已启动、进程状态未知 | 停止新派发，确认进程及候选状态后核对 |
| 用户取消目标 | 阻止新节点，传播取消；尚未证明停止的进程保留核对状态 |
| 用户暂停目标 | 立即阻止新派发；内部 Agent 在安全边界停下，外部进程按已验证能力停止或等待核对 |
| 输入、Spec、共享授权改变或产生计划修订 | 受影响结果失效；未受影响成果须经显式沿用记录才能解锁新计划节点 |
| 结果已知失败且符合重试条件 | 保留尝试，有限重试并累计费用与失败次数 |

恢复外部 session 前必须核对 Runner 版本、session 标识、工作目录、计划版本、候选摘要、授权和未决工具结果。厂商支持 resume 只说明存在恢复接口，不证明上一次动作可安全重做。当前适配器的内存会话 Map 不能作为跨进程恢复依据。

暂停首先进入 `pausing`：不创建新的节点，不派发新的模型或工具请求，正在进行的调用允许提交已知结果并继续维持租约。内部 Agent 到达安全边界后保存检查点；外部 Runner 若不支持可验证暂停，则请求停止并固化可确认的候选。只有所有活动尝试均已安全停下，目标才显示 `paused`；存在未知进程或结果时显示阻塞及待核对原因。

界面分别显示“已停止派发”“正在停止执行器”“已暂停”及“待核对”，不能把收到暂停请求当作进程已停止。恢复前重新校验当前权限、配置、成果和期限；未知副作用先核对，费用与时长累计不重置。停止导致无法继续的外部会话，只能在核对后创建明确的新尝试。

与业务系统交互时保存对方请求 ID 和业务幂等键，并在允许范围内查询实际结果。补偿也是新的副作用，单独授权与记录；“回滚”不能用来掩盖已经发送的邮件、发布或其他不可撤回操作。

## 12. 用户体验与成果验收

保留首页、工作区、收件箱、成果和活动。首页增加统一目标输入与目标卡；Agent、模型和调度细节放在可展开区域。经营视图与专业视图使用同一份计划、费用和验收状态。

| 用户阶段 | 主界面应展示什么 | 可执行操作 |
| --- | --- | --- |
| 描述目标 | 预期结果、材料、约束、缺失信息 | 补充材料、选择模板 |
| 审阅计划 | 交付清单、依赖、并行步骤、预计费用、执行方式、必要人工节点 | 调整范围、固定执行者、启动 |
| 执行中 | 当前阶段、已完成成果、等待原因、剩余额度 | 补充要求、调整方向、暂停、取消 |
| 需要处理 | 具体问题、所影响步骤、继续所需条件 | 批准/拒绝、补充信息、核对未知结果 |
| 重规划 | 保留/作废的成果、待重做步骤、新增费用和理由 | 采纳、修改或停止 |
| 验收 | 逐项标准、成果版本、检查证据、残余问题 | 接收、要求修订、拒绝 |

避免只有“运行中”和“完成”。用户应能区分生成完成、检查失败、等待批准、等待材料、待核对和已验收；也应看到外部费用是否可观测。

验收分三层：程序检查负责 schema、测试、摘要和可检查约束；独立 Agent 检查内容、证据与需求覆盖；用户决定业务取舍及是否接收。每条记录绑定成果摘要、输入版本和验收条件版本。修改成果后不能沿用旧通过记录。

Coding 保留 Spec、Governance、Harness、Sandbox、Gate 和 Evidence 的不可变绑定。OPC 保留支持证据、反证和真实承诺的区分；商业决策与付费证据仍由人确认。通用平台聚合这些检查，不能用一个模型评分覆盖领域规则。

活动记录显示“为何选这个执行者、为什么暂停、哪些检查失败、还有哪些费用未知”。不要求用户翻原始工具日志才能理解任务，也不以漂亮的进度百分比掩盖未知状态。

## 13. 两类复杂任务的完整路径

### 13.1 软件研发：增加 CSV 导入并交付可审阅变更

用户提供仓库、样例 CSV、允许修改范围、错误处理要求、测试要求和额度。协调 Agent 固定 Spec；研究节点检查现有数据流；可独立的前后端工作在不同候选副本并行，耦合部分串行。

Codex 或 Claude Code 根据明确授权承担代码候选生成；另一个内部 Agent 检查边界条件和需求覆盖。集成节点生成单一候选，权威 Gate 执行锁定测试；失败进入有限修复。最终交付固定版本的 Spec、Diff、测试事实、证据绑定、残余问题和审阅说明。未经另行授权不合并或发布。

验收必须证明：源仓库未被擅改；同一文件不存在未处理的并行冲突；声明通过的测试有真实执行证据；Spec 或候选改变后旧验收失效；崩溃恢复不会重复启动结果未知的外部 CLI。

### 13.2 经营研究：评估新产品是否进入试点

用户提供产品假设、目标客户、原始访谈和经营限制。调度器可并行派发市场及替代方案研究、反证检索、访谈信号提取；规模较小时合并为单 Agent。研究者通过获准工具查资料，分析者对照来源形成判断，独立复核检查证据是否支持结论。

交付机会档案、来源清单、反证与缺口、假设明确的成本测算、试点草案和待决定事项。研发子目标可在用户决定进入试点后启动；跨插件只通过公开契约和明确共享授权传递需求与成果。

验收必须证明：关键事实有来源和获取时间；重复来源不被当作独立证据；兴趣不能升级为购买承诺；证据不足时允许建议继续验证或暂缓。研究成功表示材料满足要求，不表示商业机会已经成立。联系客户、发布、合同和付款不会因“研究机会”而自动获得授权。

两类任务共用目标、计划、费用、交接、恢复和成果协议，领域插件保留各自的事实与验收规则。这是首版“通用”的具体范围，不承诺覆盖所有行业流程。

## 14. 分期实施与依赖

每个子计划单独评审、使用专用 worktree，并按生产行为 TDD。阶段内只增加已批准的能力，不把本文整体视作实施授权。

| 子计划 | 内容与交付 | 依赖 | 退出条件 |
| --- | --- | --- | --- |
| S0 基线与复用审查 | 对比目标/复用/跟进工作树；冻结术语、对象、事件、ADR 和测试样本 | 无 | 明确复用清单、冲突、契约和允许修改范围 |

| S2 持久节点与预算 | 独立节点 Job、幂等委派、分币种目标额度、取消及结果汇合 | S1 | 并发预算竞争和故障注入通过 |
| S3 能力与模型路由 | Agent/ModelProfile 目录、硬过滤、规则策略、决策快照 | S2 | 两种实际模型配置可按节点使用，越权候选被拒绝 |

| S6 受限外部配置 | 文件/网络隔离、可验证取消、官方审批桥接 | S4 | 逐项证明控制能力；不满足时拒绝对应任务 |
| S7 经验与策略改进 | 评测集、确认记忆、模板与跟进候选复用、事件唤醒、策略灰度 | S5 | 改进通过留出集和人工抽查；可停止订阅与新策略 |

首个完整可用版本覆盖 S0–S5，支持模型 API 和现有受信外部 Agent 委托模式；S6 才能提供经验证的更严格外部隔离。S3 与 S4 可在共同契约冻结后并行开发，集成与恢复验收必须统一进行。S7 的基础观测从 S1 开始收集，自动策略优化放在后期。

建议首版验收对象限定为本机 macOS；这是根据现有外部 Runner 支持范围提出的部署假设，尚待实施前确认。企业内部 Agent 路径同步保持契约与存储一致性，企业外部 Runner 不计入首版承诺。

投入估算仅用于排序：在 2 名熟悉仓库的工程师与兼职产品/测试支持下，S0–S5 可暂按 6–10 周规划，S6–S7 另估。真实周期取决于已有分支复用程度、外部 CLI 版本和恢复缺口；S0 结束后必须重新估算，不能当作交付日期承诺。

## 15. 验证、评测与上线门槛

### 15.1 必须覆盖的工程验证

| 类别 | 必测内容 |
| --- | --- |
| 契约 | 无环计划、schema、幂等键、并发版本、tenant/workspace 隔离、生成契约一致性 |
| 调度 | 同节点重复唤醒、依赖汇合、并行上限、配额、公平性、资源冲突和死锁防止 |
| 恢复 | 父子各阶段崩溃、迟到结果、陈旧 fencing、缺失 outbox 消费、暂停或取消时进程仍活动 |
| 模型与费用 | 跨币种分配、重复结算、未知用量、实际超预留、厂商限流、不能重置累计预算 |
| 数据与授权 | 输入撤权、记忆共享撤销、来源删除、提示注入、切换模型后数据出口检查 |
| 外部 Runner | 二进制变化、session 丢失、候选被改、结构化事件缺失、取消不可证明、版本能力变化 |
| 交付 | 伪造测试通过、缺来源、标准变化、产物摘要变化、跨计划成果沿用及重复执行阻断 |
| Shell 一致性 | Desktop 与 CLI 对同一目标得到相同状态、金额、审批及验收结果 |

测试分为确定性单元/集成测试、存储与进程故障注入、使用模拟服务的 UI 场景、真实模型和真实外部 Agent 场景。前三类通过不能代替第四类；真实服务验证使用获准账户、样本和额度，不以生产资料充当 fixture。

生产行为采用仓库完整工程基线：`npm test`、`npm run typecheck`、`npm run typecheck:desktop`、`npm run build:desktop`、Rust crate 中的 `cargo test --locked`、`npm run verify:enterprise-fixture`、`npm audit --omit=dev`，并按涉及模块执行 `npm run verify:plugins`、`npm run verify:onboarding-ui`、`npm run verify:opc-ui`、`npm run verify:coding-ui` 与相应 sandbox 检查。新子计划还需给新增场景定义具体测试入口。

Node.js 保持 `22.19.x`、npm `11.10.1`、TypeScript `5.7.2`，依赖安装使用 `npm ci`。本次文档交付只执行文档检查，不用文档检查结果证明这些产品门禁通过。

### 15.2 用任务结果衡量协作价值

建议首轮建立 30 个代表性案例：12 个研发、12 个经营研究、6 个跨领域交付；再建立独立的故障与权限矩阵。数字是建议的起始规模，不是统计充分性保证。

同一输入和验收条件下，对比单 Agent、固定工作流、多 Agent/多模型三个版本；分离日常回归集与留出集，记录模型、工具、Agent、策略及价格版本。具有随机性的代表案例重复运行并报告分布，不能只展示成功样例。

核心指标为目标验收率、每个已验收目标的总费用、完成时延、返工次数和用户主动介入次数；同时报告失败任务的消耗、关键事实可追溯率、预算未知比例及恢复成功率。费用包含协调、子节点、复核、重试和失败；外部费用未提供时单列，不能用零代入对比。

建议上线标准：测试矩阵中的越权、未知结果误重放和旧成果误验收为零；关键工程不变量全部通过；两类端到端场景均有真实执行证据。任务质量相对基线的非劣阈值、可接受时延与成本上限应在 S0 根据业务容忍度冻结，本轮不虚构提升百分比。

S7 的策略改进采用离线评估、影子选择、有限目标启用和人工抽查。影子路由仅比较选择，不能重复执行外部动作。保留旧策略供新任务回退；已执行的副作用不回滚，已产生的新版本事件也不因回退策略而降级。

## 16. 风险与实施前待定项

| 风险 | 处理方式 |
| --- | --- |
| 多 Agent 增加成本但不增加可验收价值 | 默认单 Agent；用同任务集对比，关闭无收益的拆分 |
| 动态计划导致循环、预算失控或方向漂移 | 显式验收、版本化计划、累计额度、有限重规划 |
| 外部 Agent 隐藏工具动作与费用 | 能力声明、明确委托范围、未知状态、受限配置单独验收 |
| 统一平台吞入所有领域逻辑 | 只统一执行与成果契约，领域事实留在插件 |
| 未合并工作树重复建设或混入不相关改动 | 先做 S0 复用审查，逐子计划吸收 |
| 记忆污染与过期结论传播 | 来源、有效期、用户确认、撤销传播与复核触发 |
| 自动优化损害既有任务 | 固定运行中版本，离线评估和分阶段启用 |
| 新模型/CLI 升级改变能力 | 固定版本与身份，重新准入，不热替换进行中的尝试 |

以下事项影响实施配置，但不阻碍本文作为完整方案供评审：

1. 首批实际可用的模型 API 账户与 Codex/Claude Code 运行环境。建议先验证两种内部模型配置和两种外部 Runner，使用用户已具备的账户。
2. 每类目标的费用、时长和并发上限，以及能否接受外部费用无法精确封顶。建议按工作区设置默认值，目标可收紧。
3. 数据处理范围：哪些资料允许进入云端模型或受信外部 Agent，哪些要求严格隔离或本地处理。不能从“支持多模型”推导数据共享授权。
4. 首版部署是否接受本机 macOS 优先，以及企业外部 Runner 是否另立计划。
5. 首个实施子计划是否采用 S0＋S1 的顺序。建议先审查并复用 p1-goals，再接通通用执行与验收，随后增加调度能力。
