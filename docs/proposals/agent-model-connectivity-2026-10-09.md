# Agent 检测与模型接入子计划

日期：2026-10-09。依据：用户要求判断木牛能否调度 Codex、Claude Code、WorkBuddy，并支持 Kimi、Qwen 等模型。本次范围是现有调度能力的可观测性、模型厂商接入和安全切换。

## 当前问题

- 模型仅有三个厂商预设；向导另有一份硬编码列表，无法跟随后端新增厂商。
- Runner 的 `confirmed` 只记录人工确认的文件身份，旧界面容易让用户误以为已验证登录和任务执行。
- 模型连接直接被执行和目标计划引用，原地换模型或调整旧绑定版本会改变或中断已有任务。
- WorkBuddy 桌面、CodeBuddy Code、WorkBuddy Managed Agents 是不同接入对象，不能根据安装名称判断可调度。

## 实施范围

1. 统一设置中的模型与 Agent 入口；经营视图也显示入口。
2. 提供按工作区授权的 Agent 检测接口。分项报告插件、操作权限、模型连接、文件确认、文件复查、执行进程、沙箱和外部账号验证。只被动检查已确认路径，不执行发现的程序。缺少证据保持未知，实际调用继续经过原有批准与隔离路径。
3. 接入 Kimi 中国区及 Qwen 百炼北京区。分别处理模型发现、Chat Completions、工具调用、用量与参考价格；只允许已有计费策略的模型执行。更新经核实的 DeepSeek 预设。
4. 根据厂商发现列表选择模型。选择产生独立连接，复用受保护凭据引用；新任务默认项由单独的事件与投影记录，不修改旧执行绑定。
5. CLI 与桌面使用同一契约；`doctor --workspace` 报告 Agent 条件，`model` 列出厂商和连接并选择新模型。
6. 修复安装验收发现的启动竞态：界面首次只读请求早于受管 Host 就绪时有限重试，权限与契约错误仍及时显示；不自动重试写操作。

本次不增加 WorkBuddy、CodeBuddy 执行适配器，不把外部 Coding Runner 扩大为经营 Agent，不自动传递外部 CLI 的登录凭据。模型列表探测不等于真实推理成功；安装和文件确认不等于外部 Agent 已能执行。

## 不变量与验证

保持 `/v2`、幂等键、版本检查、租户权限、受保护事实重建、不可变执行绑定、预算和沙箱拒绝策略。生产插件仍拥有宿主进程权限。

先运行失败测试，再实现模型协议、选择与状态检测。覆盖版本冲突、重复提交、未定价模型、旧绑定不变、SQLite 重开与重建、无法验证的登录态、文件变化及无 Coding 的经营工作区。运行全量测试、类型检查、桌面构建、Rust 测试、UI 真实 Host 验证、文档检查和依赖审计；企业容器与真实模型/外部账号验证分别记录环境限制，不视为通过。
