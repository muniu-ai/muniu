# 0016：提供方准备请求与正式动作分离

日期：2026-11-05。状态：E5.1 实施决定，依据[企业经营平台计划](../proposals/enterprise-operating-platform-2026-11-02.md)。

## 原因

ADR 0015 冻结五个提供方端口。最初 SDK 将完整 `ActionIntent` 用作 `prepareAction` 输入，其中已要求执行授权、预算预留和受保护输入引用。准备报价文件发生在这些正式执行记录创建之前，不能用虚构标识填充尚不存在的授权或预留。

## 决定

五个端口名称及正式 `ActionIntent`、`ActionReceipt` 保持既定语义。准备端口改用独立的 `EnterpriseProviderActionPreparation`：固定租户、工作区、操作标识、绑定版本、目标原始引用、有效期和三个动作各自的严格业务输入。正式报价准备另需已有业务批准引用。

准备只保存受保护输入与待核对文件，不改变业务事实。返回输入引用和摘要后，Host 才创建原生执行授权、预算预留和精确执行批准；正式执行使用原有 Job、租约、工具政策和回执协议。准备请求不接受执行授权、预算预留、执行批准字段或执行状态；正式报价所需的已有业务批准引用仍保留，并由提供方核验。

Host 为提供方传入已认证人员或原执行范围中的责任人，端口上下文的身份字符串本身不授予权限。执行还携带原 Job 租约，业务事实与提供方回执在同一受保护事务中保存，提交前核对当前原生执行状态。

零 token、零费用且工作预算也为零的确定性人工动作，不要求先开通模型额度；身份、职责、对象权限、业务批准、执行批准、版本和租约检查仍执行。非零预算或用量继续受原额度限制。

回执缺失不等于未执行。只有已知准备记录到期、真实原生动作与该记录的租户、工作区、操作标识、输入引用及摘要一致，且可信存储连续性检查明确通过时，才能形成未执行回执；默认没有连续性证明时维持未知，不更换操作标识重放。

## 影响

本决定细化 ADR 0015 的准备参数，不变更独立聚合、事件事实来源、Host 组合根、单一负责系统或未知结果保留规则。新增跟进任务使用独立对象流；创建任务与记录目标下一步属于同一次已批准业务动作。

接口 schema 仍是唯一来源。Sales 采用提交后冻结导出的同一 schema、解析器和契约套件，保留自己的依赖锁文件与 TypeScript 版本。未实现的 Sales 能力不能因类型声明而变为可用。实际实现和测试边界见[提供方契约说明](../enterprise-provider-contracts.md)。
