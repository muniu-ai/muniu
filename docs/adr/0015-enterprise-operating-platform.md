## 组件与事实来源

Host 装配私有 `@mn/enterprise-services`、`@mn/business-execution`、`@mn/task-orchestration`、存储及插件。Worker 可以调用私有编排与动作服务，但不另建业务控制面。企业服务负责身份、成员、对象与字段权限、职责分离和配额。动作服务负责通用承诺及回执，行业规则归提供方。

`@mn/plugin-business` 通过 contracts 与 plugin-sdk 提供领域命令、事件、指标和流程。产品插件不得导入 Kernel、Storage、Agent Runtime 或上述私有应用服务。`@mn/product-ui` 只消费生成客户端、Host 状态及 Shell 端口，Web 与 Desktop 不自行判断批准或计算权威余额。新增包在所属工作包实现时创建，不以空包表示完成。

一个 Tenant 对应客户企业，一个 Workspace 对应经营主体。业务对象独立 `streamVersion`，同一负责系统内的关联变更通过明确命令在同一事务检查全部对象版本。跨系统通过原始版本引用及回执核对，不承诺共同事务。事件使用 `KernelEventV1` 包络与受保护正文引用，领域事件必须携带重建命令结果所需的事实；新产品不以可变投影快照作为来源。

## 契约和生成来源

`enterprise-schema.ts` 冻结核心对象及结构约束，`enterprise-types.ts` 由 schema 生成。`enterprise-examples.ts` 提供 13 类核心契约的正例、所属领域事件和撤权、过期版本规格。引用类型嵌入所属事件，不要求每个引用单独成为聚合。

上述文件均位于 `packages/contracts/src/`。HTTP 请求来源为该目录的 `openapi.ts` 及其引用的 `*-api-schema.ts`，响应来源为 `api-response-schema.ts`，规划接口目录为 `enterprise-schema.ts` 中的 `ENTERPRISE_API_CATALOG`。从仓库根目录执行 `npm run generate:contracts`，再执行 `npm run docs:generate`；`generated-api.ts`、`api-outputs.ts`、`enterprise-types.ts` 和生成文档均不手工维护。

`parseEnterpriseContract` 只执行结构检查，不能授予权限或证明版本有效。当前权限、摘要绑定、跨对象作用域、时间有效性、提供方唯一归属、DAG 与预算累计分别由 E1—E5 的可信服务核验。示例中的反例是这些工作包的验收输入与预期，不是已执行授权测试。

当前 HTTP 请求来自 OpenAPI schema，响应定义集中在 `api-response-schema.ts`；请求类型、响应 DTO、运行时校验与文档从这些 schema 生成。既有领域类型可作为内部实现类型，但不再反向生成公开响应。生成文件禁止手改。

企业接口族登记在 `ENTERPRISE_API_CATALOG`，状态为 `planned`，不加入当前 Host 路由和公开 OpenAPI。对应工作包实现请求、响应、身份和版本检查后，才将具体操作加入运行时目录。命令 schema 必须按对象及命令穷举，不能接受任意代码或任意业务字段。业务写入使用 `Idempotency-Key`，已有聚合更新还需 `expectedStreamVersion`；认证回调使用 state、nonce、PKCE 和单次凭据，不套用业务幂等头。

ProviderBinding 按对象类型声明唯一负责系统及能力；首期初始化后不支持带业务数据切换模式。插件 SDK 冻结 `BusinessProviderContribution` 五端口，未支持端口返回 `not_supported`。外部版本保留提供方原始值，快照携带读取时间和权限引用。端口声明不注册连接器，也不构成执行授权。

## 权限与批准矩阵

| 主体或动作 | 对象范围和必要条件 |
| --- | --- |
| 管理员 | 组织、连接、配置和预算；不自动获得财务批准权 |
| 销售人员 / 销售经理 | 本人或显式共享客户 / 所辖团队客户；价格、成本、联系方式另按字段过滤 |
| 项目负责人 | 所管项目及获准关联订单；范围改变须核验订单版本 |
| 财务 | 获准订单的付款期、收款、退款及调整；依旧执行制单批准分离 |
| 审计员 | 授权范围内只读证据；没有业务写入和执行批准权 |
| Agent | 负责人的当前权限、职责能力、连接器权限、AuthorityRevision 与租户策略的交集 |
| 正式报价、订单生效、金额调整、客户验收、到账、退款 | 有资格人员确认或已核验外部事实；批准人与制单责任人不同 |
| 业务批准与执行批准 | 分别保存；同一合格人员可明确提交两项决定，但不得是该业务制单责任人 |
| 来源撤权与成员移除 | 每次读取、派发、工具准入、传播、恢复重新检查；未知效果只做内部核对 |

Agent 制单责任归工作或规则负责人。规则负责人离职立即暂停，接任必须接受责任并发布新授权版本。模型文本、企业微信昵称、邮箱域名和客户端 tenantId 均不能授予权限。SSE、搜索、导出、对象存储和后台任务应用相同对象与字段限制。

业务批准保存为 BusinessApproval，确认指定版本的内容能否正式采用；执行批准保存为 ExecutionApproval，允许指定摘要的一个具体动作发生。两项决定均绑定对象或动作版本，不能用其中一项替代另一项。已核验外部事实由负责系统提供来源版本和批准证据；负责系统须执行同样的职责分离，Muniu 不要求人员重复批准已经发生的事实。Muniu 发起正式报价出包时，仍须分别具备 Sales 业务批准和 Muniu 精确执行批准。

## 执行、金额与状态

Goal 使用草稿、待授权、执行中、等待人员、等待外部变化、待验收、待核对、已完成、失败、已取消十种状态。必要动作存在未知外部效果时不得完成或取消。普通通知拥有独立投递状态；仅当投递属于明确验收条件时才阻止 Goal 完成。

Authority 是唯一执行授权聚合，Mandate 表示 AuthorityRevision。计划提交与就绪 Job 原子保存。重规划仅改变未开始节点，不重复已开始动作。扩大客户范围、可写字段、外发目的地、预算或交付目标进入待授权。默认限额为每 Goal 6 个并行节点、32 个累计节点、64 次尝试、3 次自动重规划，每租户 20 个执行中节点。

入站评估在调用模型前单独预留日额度和单次额度；关联 Goal 后不重复扣费。未知费用保留预留。来源无变化不调用模型；Sales 每 300 秒轮询，每 60 秒检查持久定时键；15 分钟无持久进展仅允许一次预算内只读诊断。等待释放 Worker 槽位，人工回应和取消享有调度优先级。

业务金额为 CNY 整数分，业务日期使用 Asia/Shanghai，系统记录时间为 UTC。合同可有多个订单，一个订单对应一个项目；收款分配到付款期，超额进入待分配。部分交付、内部接收、客户验收和到账分别记录。费用缺失不显示毛利。跨系统范围变化先由 Sales 办理，再由项目负责人确认；期间暂停依赖旧范围的未执行工作。

## 新状态和后续出口

新产品默认状态根为 `~/.muniu/enterprise-v1`，覆盖变量为 `MN_ENTERPRISE_STATE_ROOT`；PG schema 为 `mn_enterprise_v1`，S3 前缀为 `enterprise-v1/`，Keychain service 为 `com.muniu.enterprise.v1`。E1 和 E6 实现并验证这些约定。E0 不修改现有启动入口，不创建或删除用户状态、密钥和数据库。

E0.1 出口包含契约生成检查、结构及生成器测试、边界测试、受影响类型检查和文档检查。E0.2 使用独立工作树，并沿用本 ADR 的结构与权限约束；真实企业依赖、双系统、模型质量和试点出口仍按完整计划执行。

E0.2 必须在 E0.1 全部出口检查通过后开始，交付 B01—U01 到工作包和验证命令的映射、每模式 30 项任务及调试/留出划分、至少 20 项安全恢复任务、人工基线量表和旧测试覆盖映射。完成判据为材料可解析、任务和要求无遗漏、划分与评分口径固定、未实现门禁明确标为未运行。该出口仅证明验收基线已冻结，不能证明对应产品能力通过验收；数量和评分细则见完整计划第 10、11 节。
